## 1. Purpose and boundary

This study validates the minimum v0.8 View and Workflow projection contracts
against pinned source code. It is not a feature-parity exercise and does not
create scope by itself.

The local checkouts live outside the Runory repository at
`/Users/yesun/Code/runory-reference-platforms`. Their exact commits, licenses,
and refresh policy are recorded in `benchmark-manifest.yaml`. No external
dependency or source code is copied into Runory.

Stripe Connect is deliberately outside this source study. Its binding contract
must continue to follow current Stripe documentation and sandbox evidence, not
an adjacent platform's payment implementation.

## 3. Source evidence

### 3.1 Twenty: View is durable product state

Relevant source:

- `packages/twenty-shared/src/application/viewManifestType.ts` declares a View
  manifest with ordered fields, filters, filter groups, groups, and sorts;
- `packages/twenty-server/src/engine/metadata-modules/view/entities/view.entity.ts`
  makes View a first-class entity with visibility and creator ownership;
- the sibling `view-field`, `view-filter`, and `view-sort` entities give those
  elements stable identity and ordering.

Evidence: a saved View is not transient component state. Stable field identity,
ordering, visibility, ownership, and typed filter/sort semantics need a durable
contract and migrations.

Runory decision: preserve `view_definitions` as the one View model and use
canonical field keys from effective metadata. Do not reproduce Twenty's
normalized View/Field/Filter/Sort/Group graph, page-layout widgets, or multiple
view modes in v0.8.

### 3.2 Directus: preference inheritance and copy-on-write

Relevant source:

- `packages/specs/src/components/preset.yaml` separates filters, layout query,
  and layout options;
- `app/src/stores/presets.ts` resolves user presets before role presets and
  global presets, and creates a user-owned copy when a user changes a shared
  preset;
- `packages/types/src/extensions/layouts.ts` separates serializable query and
  presentation options from the executable layout implementation;
- `app/src/layouts/tabular/types.ts` keeps fields/sort/page/limit distinct from
  widths, alignment, and spacing.

Evidence: shared defaults and personal preference can compose predictably, but
the effective permission filter remains separate from display preference.

Runory decision: use the order base View -> Workspace Extension -> Workspace
role default -> user preference -> permission/action filtering. A v0.8 role
default is declarative data inside the effective View; it is not another
persistent preset system or editor. User changes create only a user preference.

### 3.3 NocoBase: powerful composition has a real complexity cost

Relevant source:

- `packages/core/flow-engine/src/models/flowModel.tsx` gives every UI model a
  stable UID, sub-model tree, serializable props/step parameters, and class- and
  instance-level Flow registries;
- `packages/core/client-v2/src/flow/FlowModelRepository.ts` persists and
  duplicates those model trees;
- `packages/core/client-v2/src/flow/models/blocks/table/TableBlockModel.tsx`
  registers configurable behavior such as data scope, sorting, page size,
  selection, editing, and density;
- `packages/core/acl/src/acl-role.ts` and `acl-resource.ts` keep resource/action,
  field, and filter authorization separate from the UI model.

Evidence: a general low-code surface requires a model tree, behavior registry,
repository, editor lifecycle, and a separate ACL system. Taking only the Block
class without those responsibilities would be misleading; taking the complete
system would exceed v0.8's product boundary.

Runory decision: retain typed View configuration plus existing components and
Workspace Extension composition. Adopt the separation between declaration,
rendering, and server authorization; reject a generic Block/Flow UI runtime.

### 3.4 Frappe: pure metadata projection and append-only upgrade discipline

Relevant source:

- `ui/src/components/FormLayout/buildLayoutFromMeta.ts` purely converts flat
  field metadata and layout breaks into a tab/section/column/field tree;
- `ui/src/components/FormLayout/resolveLayout.ts` evaluates conditional
  visibility and required/read-only state without mutating shared metadata;
- `ui/src/components/FormLayout/types.ts` keeps portable field metadata apart
  from app-supplied UI overlays;
- `frappe/modules/patch_handler.py` runs recorded pre- and post-model-sync
  patches once, with transactional failure handling;
- `frappe/patches/v16_0/backfill_list_layout_route_signature.py` demonstrates a
  bounded, idempotent, batched data backfill.

Evidence: metadata should be normalized by pure functions, UI decoration should
not contaminate portable field truth, and released schema changes need ordered,
recorded migrations with bounded backfills.

Runory decision: validate and normalize legacy View data before rendering;
retain immutable released migrations and add only the next numbered migration.
Do not add Frappe's DocType builder, executable metadata scripts, or layout
inheritance system.

### 3.5 Windmill: projection follows runtime truth

Relevant source:

- `frontend/src/lib/components/FlowStatusViewerInner.svelte` derives graph and
  detail state from the job's `flow_status`, completed sub-jobs, durations, and
  failed retry job IDs;
- the same surface separates Result, Logs, Graph, Details, and Assets while
  retaining links to the authoritative job IDs;
- `frontend/src/lib/components/JobLogs.svelte` loads logs from the Job service
  rather than embedding log ownership in the view;
- `FlowStatusModule` distinguishes waiting, in-progress, success, and failure,
  and owns `failed_retries` because the Windmill Runtime actually implements
  retries.

Evidence: a useful Run view is a read projection over authoritative execution
state. Retry UI is justified only when the underlying Runtime owns attempts and
retry history.

Runory decision: add pure Workflow V2 Overview and Run projections over pinned
definition versions, instances, Work Items, and append-only events. Runory
Workflow V2 currently has no retry/attempt model or failed instance state, so
v0.8 must not invent either for visual parity with Windmill.

## 4. Adoption decisions

| Observed capability | Classification | v0.8 Runory expression | Explicit boundary |
| --- | --- | --- | --- |
| Durable, typed saved View state | **Adapt** | typed `ViewDefinition.config` with canonical field keys | no second View model or normalized View graph |
| Query state separate from presentation state | **Adopt** | filters/sort remain distinct from columns/page size | no arbitrary query JSON or SQL |
| Base/role/user preference precedence | **Adapt** | role defaults in effective View; one user preference row | no role-preset CRUD/editor or permission-group precedence |
| Permission filtering after preference composition | **Adopt** | effective permissions and governed Commands are the final filter | preference can never grant fields, actions, or permissions |
| Generic persistent Block/Flow UI engine | **Reject** | use existing `SchemaTable`, `SchemaForm`, and View contract | no low-code studio/runtime in v0.8 |
| Pure metadata-to-layout normalization | **Adopt** | pure parser/composer plus deterministic legacy normalization | no executable metadata scripts |
| Ordered, recorded migration and bounded backfill | **Adopt** | next numbered Runtime migration; no released-migration edits | no opportunistic schema repair at render time |
| Business-readable Run projection | **Adapt** | project Workflow V2 version, events, and Work Items | no second Workflow Runtime or canvas |
| Retry/attempt visualization | **Defer** | none until Workflow V2 owns retry semantics | do not infer retries from returns or repeated events |
| General logs/assets/sub-job explorer | **Defer** | only safe event/Work Item details required by the FSM journey | no user-script execution or general observability product |

## 5. Complexity assessment

| Area | Accepted v0.8 impact |
| --- | --- |
| Runtime | pure View and Workflow projection functions; no new UI runtime or Workflow execution state |
| Data | one user preference table and existing next-numbered migrations; no role-preset or View-child tables |
| UX | shared list/form behavior and a read-only Workflow Overview/Run surface; no builder concepts |
| Delivery | deterministic legacy normalization, diagnostics, migration, and reference-surface tests |
| Ecosystem | source study only; no new dependency, copied code, or upstream runtime coupling |

## 6. Resulting specification corrections

This study requires these binding corrections:

1. define the bounded View preference overlay and Workspace-role default
   explicitly;
2. persist optional user page size alongside visible fields, exact filters, and
   sort;
3. state that canonical field keys, not database-specific metadata IDs, are the
   portable View identity;
4. remove unsupported Workflow `failed` and retry promises from v0.8;
5. project only states and history already owned by Workflow V2, including
   running, completed, returned, and cancelled outcomes;
6. keep logs, retry attempts, a builder, and a second Runtime deferred.

These corrections narrow v0.8. They do not add another structural workstream.
