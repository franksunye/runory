## 1. Purpose and non-retroactivity rule

The external-platform research and engineering benchmark roadmap were added
after v0.6.0 and v0.7.0 were released. This review maps the newer benchmark
language to release evidence without changing the scope, commit, or Tag of
either release.

```text
new benchmark language
→ map to existing Runory evidence
→ identify any real residual gap
→ schedule that gap forward
→ never redefine an already released Tag silently
```

A later benchmark cannot make an earlier release incomplete by definition.
When it reveals a capability that is necessary before GA, that capability
receives a new owner, target milestone, and acceptance boundary.

## 4. Forward work item: `V09-FIN-01`

Title: Minimum Payment Reconciliation and Diagnostics
Owner: Payments / Platform / Operations
Target: v0.9, before public-contract freeze

Required scope:

1. retrieve the current provider snapshot for one Workspace Payment;
2. compare provider account, reference, currency, amount, payment status, and
   refunded amount with Runory authority;
3. return and persist an auditable result of `consistent`, `divergent`, or
   `unknown`, with safe diagnostic details;
4. expose the result to an authorized operator;
5. allow only named, idempotent reconciliation/replay actions that preserve
   legal transitions and existing Invoice allocation invariants;
6. test lost, duplicate, delayed, reordered, and refund events plus cross-tenant
   and wrong-provider-account rejection.

Explicit non-goals:

- bank-statement or bookkeeping reconciliation;
- general ledger, journal entries, credit notes, or accounting export;
- payout, balance, settlement, fee, tax, or dispute management;
- bulk repair through direct database mutation;
- a provider-specific mutation path outside Commands and audit.

Acceptance evidence:

- a missed provider event becomes an operator-visible discrepancy;
- a supported replay/reconcile action converges Payment and Invoice state
  idempotently;
- an unsupported or ambiguous mismatch remains visible and requires escalation;
- repeated reconciliation does not duplicate Payment, allocation, refund,
  domain event, or audit outcome;
- no cross-Workspace provider or financial data is exposed.

## 5. Final conclusion

```text
v0.6  benchmark mapping complete; no code backfill
v0.7  released financial invariants remain accepted
v0.9  implement only V09-FIN-01 before contract freeze
```

The benchmark adoption process has therefore found one necessary forward
hardening item, not a reason to repeat v0.6 or v0.7.
