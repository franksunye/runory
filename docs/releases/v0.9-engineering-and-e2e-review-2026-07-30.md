## 1. Review purpose and scope

This review evaluates the recent v0.9 implementation and the beginning of E2E
acceptance against two obligations:

1. engineering changes must preserve Runory's architecture, domain authority,
   Command, transaction, tenancy, Module/Pack/Template, upgrade, and extension
   principles;
2. E2E must become the release-closing mechanism for functional correctness,
   permissions, data integrity, cross-surface coherence, recovery, and product
   experience.

The reviewed change range contains approximately 11,210 added lines and 616
deleted lines across Workflow Runtime, Quote and Invoice behavior, scheduled
Workflow timers, Command execution, data-integrity tests, the API walkthrough,
and the new manual E2E suite.

## 2. Release decision

**FAIL — v0.9 implementation breadth is substantial, but the release is not
engineering- or E2E-closed. It must not yet be represented as meeting the v0.9
Definition of Done.**

The primary reasons are:

- the canonical Quote-to-Invoice journey has a reproducible amount-integrity
  regression;
- the production Workflow Timer Cron cannot be invoked by Vercel;
- normal Work Item completion leaves timers active;
- demo provisioning creates known errored Workflow instances;
- the automated walkthrough and the current run-record policy can produce
  false-positive PASS results;
- the required real-customer cohort and repeatability evidence is not present
  in the repository.

This decision does not reject the v0.9 direction. The provisioning,
configuration Diff, health, diagnostics, payment reconciliation, Web Push,
upgrade, rollback, contract-freeze, and extension-template foundations are
present and materially advance the product. The decision means those
capabilities have not yet been proven together at the release-contract level.

## 4. Engineering findings

### V09-REV-ENG-01 — P0: Quote calculation no longer owns line totals

Location: `packages/platform-core/src/quote-calculation.ts`, lines 58–63.

`prepareQuoteCalculation()` now preserves every non-null `line_total`, including
a stale, manually entered, or client-supplied value. This contradicts the same
file's authority statement that Quote totals are calculated server-side and
that governed amount fields are written by `quote.recalculate`.

The regression is directly observable in the canonical journey:

```text
line inputs: quantity=2, unit_price=2000, discount=200, tax=280
derived line total: 4080
persisted line total: 0
Quote grand total: 8240
Invoice source line total: 4160
result: INVOICE_TOTAL_MISMATCH
```

Required correction:

- always derive and overwrite `line_total` from authoritative inputs;
- reject or ignore a caller-supplied governed line total;
- keep Quote line mutation and Quote total recalculation in one atomic Command
  effect rather than a best-effort post-write hook;
- retain the existing canonical test as a blocking regression gate.

### V09-REV-ENG-02 — P1: Quote recalculation bypasses the governed Command boundary

Location: `packages/platform-core/src/metadata.ts`, lines 66–84 and its
create/update/delete call sites.

The generic metadata CRUD layer now detects the domain-specific `quote_line`
object and calls `recalculateQuote()` after the record write. Any recalculation
error is swallowed. This creates states in which the line mutation succeeds but
the governed Quote totals remain stale.

This violates the intended direction of ADR-004 and ADR-035:

```text
UI / API
→ named Command
→ Contract + capability Provider
→ atomic line and Quote writes
→ event + audit
```

Domain-specific Quote behavior should not accumulate in the generic metadata
runtime. Introduce or complete named Quote Line Commands and express
recalculation as a required atomic effect.

### V09-REV-ENG-03 — P0: Vercel cannot invoke the Workflow Timer Cron

Locations:

- `apps/cloud/vercel.json`, lines 4–9;
- `apps/cloud/src/app/api/platform/cron/workflow-timers/route.ts`, line 26.

Vercel Cron sends an HTTP GET request to the configured path. The registered
route exports only `POST`, and a local GET to the configured path returns 405.
Production SLA warning and overdue processing therefore never starts.

Required correction:

- expose the authenticated implementation through GET;
- optionally keep POST for local/operator invocation by delegating both methods
  to one handler;
- add a route-level test that invokes the configured method with `CRON_SECRET`;
- add a deployed smoke check that proves one due timer is processed.

### V09-REV-ENG-04 — P1: Terminal Work Items retain active SLA timers

Locations: `approvalDecideHandler`, `returnWorkItemHandler`, and
`completeWorkItemHandler` in `packages/platform-core/src/workflow.ts`.

Workflow cancellation cancels active timers, but approval, normal completion,
and return transitions do not. Once the Cron entry is fixed, a timer belonging
to an already completed or returned item can still emit `timer.sla_warning` or
`timer.overdue`.

Effects include false notifications, incorrect timelines, misleading support
diagnostics, and corrupted repeatability/SLA metrics.

Required correction:

- cancel or supersede the old Work Item timer in the same transaction as every
  terminal or replacement transition;
- create a new timer when return creates a replacement Work Item;
- filter timer processing against actionable Work Item and running Workflow
  state as defense in depth;
- test complete-before-deadline, return-before-deadline, cancel, and Cron race
  cases.

### V09-REV-ENG-05 — P1: Demo delivery treats errored Workflows as successful seed state

Location: `packages/platform-core/src/installer.ts`, lines 1045–1094.

The demo installer calls the general `startWorkflow()` path for seeded Quotes
that are already `in_review`. The definition's first executable step is
`quote.submit_for_approval`, for which no system-command executor is registered.
The instance is marked `error`.

The recent idempotency change includes `error` in the existing-instance query,
preventing duplicates but preserving the invalid state. Test output confirms
the error repeatedly while pack tests still pass.

Required correction:

- use the same start semantics as the atomic `workflow.start_process` Provider,
  which skips the triggering Command and lands at the actionable approval step;
- make demo-data load fail when it produces an errored Workflow;
- include zero errored Workflow instances in provisioning health acceptance.

### V09-REV-ENG-06 — P1: v0.9 completion lacks binding cohort evidence

The v0.9 Definition of Done requires:

- 3–5 real FSM businesses operating the canonical journey;
- a 90/10 report for each customer;
- zero customer-specific Core forks;
- implementation time, intervention, support, reliability, adoption, and
  upgrade-effort measurements;
- real-customer validation of health, diagnostics, Web Push, and upgrade;
- upgrade to the frozen product without data or behavior loss.

The repository contains the relevant tools and plan, but not the required
customer acceptance records or metrics. Until these exist, the correct status
is "implementation substantially complete; v0.9 acceptance in progress."

## 5. E2E review findings

### V09-REV-E2E-01 — P0: The automated walkthrough can return a false PASS

Location: `apps/cloud/scripts/e2e-walkthrough/run-business-walkthrough.mjs`.

False-positive paths include:

- Scenario 2 returns early after a missing approval Work Item and never appends
  its failed summary;
- Scenario 3 falls back to any seeded Work Order when Quote conversion fails;
- missing Work Order or Visit is recorded as `{ pass: 0, fail: 0 }`;
- the grand summary only sums scenarios that reached result registration.

Required correction:

- required prerequisite absence must record at least one failure;
- register every Scenario result in `finally`;
- remove seeded-record fallback from the canonical journey;
- generate one Run ID and require every downstream aggregate to trace to the
  records created by that run;
- treat required `SKIPPED` and `BLOCKED` as a non-zero process exit.

### V09-REV-E2E-02 — P1: The current PASS record violates the suite's own contract

The only current Quote Commercial Loop record marks the run `PASS
(conditional)` despite:

- one skipped required stage;
- three untested required stages;
- unresolved P1 findings;
- a lifecycle path that did not exercise return/resubmit or withdrawal.

The E2E README permits PASS only when every required stage passes and no P0/P1
remains. The record must therefore be classified as FAIL and retained as useful
discovery evidence, not release-acceptance evidence.

### V09-REV-E2E-03 — P1: API walkthrough evidence is being conflated with browser E2E

The 117-assertion walkthrough is valuable system/API integration coverage, but
it operates mainly through API helpers and explicitly excludes payment and
billing. It cannot prove UI discoverability, interaction sequencing, responsive
behavior, visual feedback, Service Worker behavior, or real device/provider
delivery.

The suite needs explicit evidence labels:

```text
contract/integration test
API business walkthrough
automated browser E2E
manual device/provider acceptance
real-customer release evidence
```

No lower layer may be reported as satisfying a higher layer.

### V09-REV-E2E-04 — P2: Run evidence and documentation are not yet governable

Problems observed:

- README says records belong in `docs/releases/manual-e2e-runs/`, while the
  current record lives under `docs/testing/manual-e2e/run-records/`;
- README related-document links use the wrong relative depth;
- the run record lacks required evidence metadata;
- no machine-readable run result binds commit, environment, Scenario results,
  evidence artifacts, and finding IDs.

## 6. Target E2E architecture

E2E should be a release-evidence system, not one large script or a collection
of manual checklists.

### 6.1 Layered gates

> **Authority note (2026-07-31):** the binding G0–G5 means for v0.9 release
> acceptance are defined in
> [v0.9 E2E Gate Remapping — 2026-07-31](v0.9-e2e-gate-remapping-2026-07-31.md).
> The table below is retained as historical design context from this review.

| Layer | Purpose | Frequency | Blocking rule |
| --- | --- | --- | --- |
| G0 Architecture and contract | Command ownership, atomicity, tenancy, migration, compatibility, concurrency | every PR | any failure blocks merge |
| G1 API business walkthrough | deterministic multi-role aggregate journey and cross-surface data contracts | every PR | required Scenario failure/skip blocks merge |
| G2 Browser P0 journey | real UI actions for Quote → Work Order → Visit → Invoice → Payment | every PR or protected merge queue | any P0 journey failure blocks merge |
| G3 Nightly breadth | roles, exceptions, retry, refresh, weak network, mobile viewport, accessibility, performance | nightly | regression blocks release branch |
| G4 Device/provider acceptance | Stripe, Web Push, PWA install, iOS/Android, 404/410 cleanup | release candidate | missing evidence blocks release |
| G5 Customer repeatability | provisioning, 90/10, upgrade/rollback, metrics across 3–5 customers | v0.9 release | missing customer evidence blocks v0.9 completion |

### 6.2 Assertions required at every business stage

Each stage should cover the applicable dimensions:

1. **Affordance** — the intended actor can find and understand the next action;
2. **Authorized outcome** — the action succeeds only for the allowed actor;
3. **Denied outcome** — an unauthorized actor is rejected server-side and the
   UI does not falsely imply success;
4. **Domain invariant** — authoritative state, versions, amounts, relations,
   evidence, and tenant scope are correct;
5. **Traceability** — Command, Domain Event, Audit, Workflow, and timeline agree;
6. **Cross-surface coherence** — list, detail, planning, My Work, mobile, portal,
   and diagnostics show the same outcome;
7. **Recovery** — refresh, retry, duplicate submission, timeout, and provider
   redelivery do not duplicate or corrupt results;
8. **Experience** — loading, error, empty, success, disabled, and next-action
   states are understandable without architecture knowledge.

### 6.3 Result model

Allowed stage results:

```text
PASS     all required assertions and evidence are present
FAIL     behavior or invariant is wrong
BLOCKED  external prerequisite unavailable; never release-passing
N/A      explicitly outside this Scenario's binding scope
```

`SKIPPED` is not a passing result for a required stage. Conditional PASS is not
an allowed final release decision.

Each automated run should emit a machine-readable artifact containing:

```text
runId / commit / environment / browser / viewport / principals
fresh aggregate IDs and their trace chain
stage results and durations
screenshots, trace, console and network failures
API and DB invariant evidence
finding IDs and severity
final PASS or FAIL
```

## 7. Required v0.9 closure sequence

### Gate A — Restore the engineering baseline

- [ ] Revert or correct stale `line_total` preservation.
- [ ] Move Quote Line mutation and recalculation behind an atomic Command path.
- [ ] Restore the canonical FSM and full repository test suites to green.
- [ ] Make Vercel Cron invoke the correct HTTP method.
- [ ] Cancel timers on complete, approve, return, and cancel transitions.
- [ ] Eliminate seeded errored Workflows and fail provisioning health on them.

### Gate B — Make E2E results trustworthy

- [ ] Remove fallback to seeded downstream aggregates.
- [ ] Make every required skip or missing prerequisite fail the run.
- [ ] Record every Scenario result even after exceptions or early termination.
- [ ] Introduce one traceable Run ID across the whole commercial lifecycle.
- [ ] Move run records to the governed release-evidence location.
- [ ] Replace `PASS (conditional)` with the binding PASS/FAIL model.

### Gate C — Automate the P0 browser journey

- [ ] Fresh Workspace/data setup through supported provisioning APIs.
- [ ] Quote create/edit/recalculate/submit/return/resubmit/approve/send/accept.
- [ ] Convert to Work Order and verify inherited customer/site/asset context.
- [ ] Dispatch, assignment, schedule, mobile execution, evidence, and completion.
- [ ] Invoice issue, Stripe payment, refund, and reconciliation.
- [ ] Customer-access acceptance and revoked-access denial.
- [ ] Screenshot, trace, console, network, audit, and DB-invariant artifacts.

### Gate D — Produce binding release evidence

- [ ] Execute all P0/P1 manual suites with no unresolved P0/P1 findings.
- [ ] Complete real iOS/Android Web Push and PWA acceptance.
- [ ] Complete upgrade and rollback on production-shaped workspaces.
- [ ] Publish one 90/10 and repeatability report for each of 3–5 customers.
- [ ] Evidence zero Core forks and zero direct business-data bypasses.
- [ ] Re-run full regression and publish the final v0.9 acceptance decision.

## 8. Acceptance rule after remediation

v0.9 can be marked complete only when all of the following are simultaneously
true:

```text
G0–G4 release gates                  PASS
canonical commercial browser path   PASS
unresolved P0/P1 findings           0
required skipped/blocked stages     0
real FSM customer cohort            3–5
customer 90/10 reports              PASS for every customer
customer-specific Core forks        0
upgrade data/behavior regressions    0
repeatability metrics               meet documented targets
```

Until then, the recommended external and internal release statement is:

> v0.9 feature implementation is substantially complete. Engineering
> regression repair and release-level E2E/customer evidence are still in
> progress.
