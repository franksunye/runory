## 1. Decision

Runory will not copy Twenty's UI architecture. It will adapt the smallest
proven interaction and presentation patterns to Runory's existing contracts,
technology stack, data scale, and governed business model.

The binding direction is:

```text
Runory contracts and authorization
→ pure presentation policy
→ lightweight shared components
→ schema-driven list/detail/form surfaces
```

Twenty remains evidence for interaction quality, saved-view behavior, field
presentation, and state clarity. It does not become the owner of Runory's
component model, client state, extension mechanism, table engine, styling, or
page layout.

This decision does not reactivate deferred v0.8 Batch 2 and does not block the
active customer-access, payment, or Workflow batches. It governs incremental
shared UI work now and Batch 2 if it is resumed before GA.

## 2. Current constraints

The decision is based on the implemented Runory baseline:

- Next.js 15 App Router, React 19, Tailwind CSS 4, CSS custom properties, and
  SWR;
- one Cloud frontend under `apps/cloud`; there is no second consumer that
  justifies a separate UI package;
- one typed View contract, a closed `FieldType` set in `@runory/contracts`,
  Workspace Extension field/view composition, and permission-filtered
  `ViewAction` data;
- one metadata-driven dynamic object route shell already renders installed
  objects, extension fields, and safe small Workspace-owned custom objects;
  broader user/Agent-created objects are an intended evolution of this same
  declarative model;
- schema-driven `ObjectListPage`, `ObjectDetailPage`, `SchemaTable`, and
  `SchemaForm` already exist and are Client Components because they use SWR,
  router, locale, permission, and interactive form state;
- normal object datasets are hundreds to low thousands of records; there is no
  measured need for client table virtualization;
- Module and Workspace Extension contracts do not provide executable frontend
  plugin entry points.

These are useful constraints. A proposed abstraction must simplify this system,
not create a second UI runtime beside it.

## 3. Binding invariants

1. View, field, action, permission, and Command authority remain in Runory
   contracts and Platform Core; UI components do not invent them.
2. Permission-filtered rendering is not authorization. Every read and Command
   is still authorized on the server.
3. Installed, Workspace-owned, and future dynamically created objects use the
   same versioned field and View contracts. They may add or rearrange
   declarative metadata but cannot register executable UI code.
4. Shared UI components remain in `apps/cloud` until a real second product
   consumer proves that a package boundary reduces total complexity.
5. No state manager, table framework, styling system, component generator, or
   UI plugin runtime is added without a measured problem and a separate
   decision.
6. Existing pages migrate incrementally. UI consistency does not justify a
   repository-wide visual rewrite.
7. Loading, empty, error, not-found, and partial-success are different domain
   states; a generic hook must not erase those distinctions.

## 4. Adopt / Adapt / Defer / Reject

| Twenty or candidate pattern | Decision | Runory expression |
| --- | --- | --- |
| Semantic design tokens | **Adapt** | retain current tokens and Tailwind classes; add a token only when a shared component needs a missing semantic value |
| Consistent loading/empty/error presentation | **Adopt** | small presentational state components with explicit page-level state mapping |
| Unified generic SWR `SurfaceState` hook | **Reject** | pages retain domain-aware branching; shared components render, they do not own fetching policy |
| Metadata-driven field display | **Adapt** | one exhaustive renderer table for the closed Runory `FieldType` union plus a safe legacy fallback |
| Runtime `registerFieldDisplay()` extension slot | **Reject** | new field types require a versioned contract, compatibility review, renderer, and tests |
| Saved-view behavior | **Adapt** | URL owns explicit transient query; preference stores user defaults; URL overrides preference |
| Shared page/section headers | **Adopt** | thin components encoding the current Runory visual language |
| Full Card/Typography system | **Defer** | retain `.app-card`; extract only repeated structure proven on at least three reference surfaces |
| shadcn CLI/component import | **Reject for this batch** | no new component source or configuration is needed for state, header, and field primitives |
| Twenty SCSS/Jotai architecture | **Reject** | retain Tailwind, CSS variables, local React state, and SWR |
| HTML table and incremental pagination | **Adopt** | improve existing `SchemaTable`; fix server pagination before considering virtualization |
| Twenty treadmill virtualization | **Reject** | no measured scale need and no custom virtualization code |
| TanStack Table/Virtual | **Defer** | reconsider only after server pagination and performance evidence show a remaining UI bottleneck |
| Mobile record-card fallback | **Adapt** | use existing responsive CSS and the same field/action resolvers; container queries only when an embedded-width case proves necessary |
| Widget/PageLayout runtime | **Reject** | keep stable detail-page structure driven by effective View sections and existing related/workflow panels |
| Broad Server Component migration | **Reject for this batch** | keep current Client Component boundaries; new pure primitives should remain RSC-compatible where practical |
| Inline editing, column DnD, row selection, command menu | **Defer** | require repeated workflow evidence and explicit Command/interaction semantics |
| Dark theme and wide-gamut palette | **Defer** | no current milestone requirement |
| General partial-data state | **Defer** | admit only when an API exposes a typed partial-success contract and recovery action |

### 4.1 Dynamic-object readiness

Runory's object set is not permanently fixed at build time. The UI must render
an object it did not know by name when the frontend was authored, provided the
object uses admitted metadata, field types, views, permissions, and generic
CRUD/Workflow capabilities.

That requirement strengthens this decision rather than requiring Twenty's full
Widget Runtime:

- renderers dispatch on versioned field type, never on a hardcoded object list;
- list/form/detail structure comes from the effective View and object metadata;
- dynamic objects receive the shared route shell and state components
  automatically;
- authoritative business invariants still require governed Commands or an
  Extension Module instead of arbitrary metadata mutation;
- a genuinely new field primitive is a versioned platform-contract change,
  while a new object assembled from existing primitives requires no frontend
  release.

This gives Runory dynamic-object flexibility without accepting executable
frontend plugins, arbitrary widgets, or a second authorization model.

## 5. Component boundary

The minimum shared layer is deliberately small:

```text
apps/cloud/src/components/ui/
  SurfaceLoading.tsx
  SurfaceEmpty.tsx
  SurfaceError.tsx
  PageHeader.tsx
  SectionHeader.tsx

apps/cloud/src/components/fields/
  FieldDisplay.tsx
  field-display-renderers.tsx
```

Names may follow an existing repository convention when implemented, but the
responsibility boundary is binding:

- state components render accessible presentation only;
- field renderers format already-authorized values only;
- page components decide which state applies and which recovery action is
  valid;
- API hooks own fetching/revalidation;
- View/action resolvers own configuration composition and presentation policy;
- server APIs and Command Runtime own authorization and mutations.

Do not add `SurfaceStateRenderer`, `useSurfaceState`, a component registry
service, or a UI package merely to make the directory look like a design
system.

### 5.1 State component contract

Use three shared primitives initially:

- `SurfaceLoading`: `table | detail | form | page` visual shapes, `aria-busy`,
  reduced-motion compatible;
- `SurfaceEmpty`: icon, title, optional description, and an already-authorized
  action supplied by the page;
- `SurfaceError`: safe message, optional retry supplied by the page, and an
  alert/live-region treatment that does not expose internal errors.

Not-found remains an explicit page state, normally expressed through
`SurfaceEmpty` with not-found copy. No-permission remains an authorization
response, not an empty state. Partial success uses an inline notice only after
the API contract identifies what succeeded, what failed, and what retry means.

### 5.2 Layout primitives

`PageHeader` and `SectionHeader` may be extracted because the current pattern is
repeated and semantically clear. `.app-card`, `.app-button-*`, `.app-input`, and
`.app-skeleton` remain the visual foundation.

A `Card/Header/Content/Footer` family is not required until three real consumers
need divider, padding, or footer behavior that `.app-card` cannot express
without duplication. Modal/dialog work is outside this decision; a future
dialog must provide focus management, escape handling, labelling, and keyboard
access rather than standardizing today's ad-hoc overlay markup.

## 6. Field presentation contract

The renderer set follows the closed contract:

```ts
const FIELD_DISPLAY_RENDERERS = {
  text: TextDisplay,
  email: EmailDisplay,
  phone: PhoneDisplay,
  number: NumberDisplay,
  date: DateDisplay,
  select: SelectDisplay,
  boolean: BooleanDisplay,
  lookup: LookupDisplay,
  user: UserDisplay,
} satisfies Record<FieldType, FieldDisplayRenderer>;
```

This gives constant lookup and compile-time exhaustiveness without introducing
runtime registration. A persisted legacy/invalid type renders a neutral text
fallback and emits a bounded diagnostic; newly published manifests continue to
fail contract validation.

Formatting rules:

- empty values render one consistent em dash;
- number and date use the active locale;
- email and phone use safe `mailto:`/`tel:` links;
- lookup renders the resolved display value and an authorized internal route;
- user renders the resolved identity label and avatar when available;
- boolean uses localized yes/no text;
- select uses its declared option label and a neutral badge by default.

The current contract does not contain `currency`, option-color metadata, or a
frontend extension entry point. The UI must not pretend that they exist.
Semantic option tones require a later typed metadata addition; they must not be
guessed globally from values such as `open`, `paid`, or `failed`. Domain-specific
financial formatting may remain in the owning governed surface until a real
shared contract is approved.

## 7. List and table standard

`SchemaTable` remains a semantic HTML table with incremental pagination.

When this work is activated, add only:

1. skeleton rows that match the active column count;
2. explicit empty/error presentation supplied by `ObjectListPage`;
3. width mapping from the existing View column contract;
4. all cell values through `FieldDisplay`;
5. a responsive record-card rendering for the agreed reference surfaces;
6. one centralized resolver for permitted actions and their UI placement.

The existing `ViewAction` contract does not explicitly distinguish collection
header, record-row, record-header, and form-footer placement. Therefore the UI
must not render every action in every location. Legacy `create` and `view` may
retain their current normalized behavior; any new ambiguous placement requires
a small View-contract amendment before implementation.

Before introducing virtualization, prove all of the following:

- server-side bounded pagination already exists;
- the supported dataset and viewport produce a measured rendering bottleneck;
- the target interaction cannot be solved by pagination or reduced columns;
- a maintained headless library is preferable to custom virtualization.

## 8. URL and saved-preference standard

The effective list state resolves in this order:

```text
typed View defaults
→ effective Workspace-role defaults
→ current-user preference
→ explicit URL query parameters
→ permission and governed-action filtering
```

Rules:

- `q`, active exact filters, and explicit sort may be represented in the URL so
  refresh, back/forward, bookmarking, and sharing behave predictably;
- an explicit URL value wins over a saved preference;
- absence of a URL value allows the saved preference/default to apply;
- visible fields and page size are normally personal preferences, not noisy URL
  state;
- a deliberate Save action persists visible fields, filters, sort, and page
  size through the existing optimistic-lock API;
- typing in search or opening a shared URL must not silently overwrite a saved
  preference;
- unknown or unauthorized URL fields are rejected or removed by the typed
  resolver before a request is made.

This is not Twenty's Jotai/URL dual synchronization and does not require a new
state library or a Server Component rewrite.

## 9. Responsive and accessibility standard

Use the existing Tailwind breakpoints first. A record-card fallback must reuse
the same effective columns, `FieldDisplay`, action filtering, and record URL as
the desktop table; it must not create separate business logic.

For v0.8 reference acceptance:

- 320 px, 768 px, and desktop widths have no unreachable action or unintended
  horizontal page scroll;
- keyboard focus order follows visual order;
- icon-only actions have accessible names;
- loading does not announce repeatedly during SWR revalidation;
- errors are announced once and retry is keyboard accessible;
- motion respects `prefers-reduced-motion`;
- table headers remain semantic, and card labels preserve field/value meaning.

Container queries are allowed later for a proven embedded-width problem. They
are not the default merely because Tailwind supports them.

## 10. Implementation sequence when activated

### Slice A — shared policy and primitives

- extract the exhaustive field renderer and three state primitives;
- centralize action placement for existing `create`/`view` behavior;
- add unit tests for pure field/action/state policy;
- make no visual redesign.

### Slice B — three reference surfaces

- apply the primitives to Contact/Company, Work Order, and Invoice list/detail
  paths;
- remove hardcoded `status`/`priority` rendering from `SchemaTable`;
- add explicit loading, empty, error, and not-found behavior;
- prove desktop and narrow-screen behavior.

### Slice C — preference UI

- implement the resolution order in section 8;
- persist only on an explicit Save action with expected version;
- verify URL override, clear/reset, stale-version conflict, and permission
  filtering.

### Slice D — proportional rollout

- roll shared primitives to other schema-driven surfaces only where they
  replace duplication;
- record remaining intentional domain-specific views;
- stop before widget layout, runtime renderer plugins, inline editing, or a
  table framework.

## 11. Verification and exit criteria

The UI decision is correctly implemented when:

1. the three reference surfaces share state presentation and field formatting;
2. no shared table code branches on `fieldKey === "status"` or
   `fieldKey === "priority"`;
3. every contract `FieldType` has a compile-time checked renderer and invalid
   legacy data has a visible fallback;
4. actions are permission-filtered in the UI and re-authorized on the server;
5. URL state and saved preference follow the documented precedence without
   implicit preference writes;
6. responsive and keyboard acceptance passes at the stated widths;
7. repository tests, typecheck, build, and relevant contract tests pass;
8. no new UI runtime, state manager, table library, component generator,
   executable extension slot, or duplicate View model was added;
9. the implementation removes more page-specific code than shared abstraction
   code it introduces.

Do not use a fixed historical test count as a gate. Visual regression tooling
is a separate investment decision; until it exists, record bounded manual
responsive/accessibility evidence rather than claiming automated visual
coverage.

## 12. Final rule

```text
Borrow Twenty's product-quality lessons.
Keep Runory's contracts, stack, and business semantics.
Extract only repeated behavior.
Measure before adding infrastructure.
```
