## 1. Purpose

This document is the Batch 0 exit gate. It records the verified current state
of every Runory foundation that v0.8 extends, classifies each benchmark
capability against the External Benchmark Adoption Guardrails, maps every
admitted item to its existing Runory model, and freezes the acceptance
fixtures that subsequent batches must satisfy.

No implementation work begins until this inventory is reviewed and the scope
is frozen.

## 3. Adopt / Adapt / Defer / Reject matrix

| Observed capability | Classification | v0.8 Runory expression | Explicit boundary |
| --- | --- | --- | --- |
| Durable, typed saved View state | **Adapt** | Typed `ViewDefinition.config` union with `schemaVersion: "1.0"` | No second View model or normalized View graph |

| Base/role/user preference precedence | **Adapt** | `workspaceRoleDefaults` inside effective View config; one `view_preferences` row per user/view | No role-preset CRUD/editor or permission-group precedence |
| Permission filtering after preference composition | **Adopt** | Effective permissions and governed Commands are the final filter in composition order | Preference can never grant fields, actions, or permissions |
| Generic persistent Block/Flow UI engine | **Reject** | Use existing `SchemaTable`, `SchemaForm`, and typed View contract | No low-code studio/runtime in v0.8 |

| Retry/attempt visualization | **Defer** | None until Workflow V2 owns retry semantics | Do not infer retries from returns or repeated events |
| General logs/assets/sub-job explorer | **Defer** | Only safe event/Work Item details required by the FSM journey | No user-script execution or general observability product |
| Customer access grant model | **Adapt** | New `runory.customer-access` Platform Service with grant/session/audit | Not a general Customer Portal; no customer identity or account admin |

## 5. Five-area complexity impact assessment

### 5.1 View contract convergence (Batch 1)

| Area | Accepted v0.8 impact |
| --- | --- |
| Runtime | Pure View config validation and composition functions in Platform Core; no new UI runtime. Legacy normalization adapter runs at parse time. |
| Data | One new `view_preferences` table via next numbered migration. Existing `view_definitions` rows unchanged — `config_json` parsed through new schema at read time. |
| UX | Shared list/form behavior driven by effective View contract. Role defaults and user preferences are declarative data, not an editor. No builder concepts. |
| Delivery | Deterministic legacy normalization, catalog validation upgrade, migration, and reference-surface tests. Three parallel `ViewConfig` types consolidate into one shared type from `@runory/contracts`. |
| Ecosystem | No new dependency. Source study only; no copied code. |

### 5.2 Customer access and merchant-owned payment (Batch 2)

| Area | Accepted v0.8 impact |
| --- | --- |
| Runtime | New `runory.customer-access` Platform Service (grant/session/audit only). New `authorizeCustomerCommandActor` branch in Command Runtime. Stripe Connect adapter extension (onboarding, Direct Charge context, Connect webhook). No new payment aggregate or checkout path. |
| Data | One new `customer_access_grants` table. Extended `payment_provider_account` with Connect fields (onboarding_status, charges_enabled, payouts_enabled, requirements). No second account-ID mapping. |
| UX | One public `/:locale/access` page with 9 states. One operator payment-settings surface showing onboarding status. No Workspace navigation, no customer account settings. |
| Delivery | New public API routes (exchange, context, accept, checkout, logout). New authenticated API routes (grants CRUD, Connect onboarding/sync/disconnect). Stripe Connect sandbox setup for two merchants. |
| Ecosystem | Stripe SDK (already a dependency). No new external dependency. Connect webhook requires a separate signing secret registered in Stripe Dashboard. |

### 5.3 Workflow visibility (Batch 3)

| Area | Accepted v0.8 impact |
| --- | --- |

| UX | Business-readable Overview and Run views. Step sequence, current step, completed path, pending work, approval outcome. No drag/drop, canvas, or retry explorer. |

## 7. v1.0 GA contract reconciliation

The v1.0 GA Release Goal (`v1.0-ga-release-goal.md`) defines a 90% product /
10% extension contract. Batch 0 reconciles it with the one-shape roadmap:

| v1.0 GA promise | v0.8 status | Reconciliation |
| --- | --- | --- |
| Customer portal identity and scoped access | v0.8 delivers minimum customer access (expiring grant, not portal identity) | Full portal deferred to post-1.0; v0.8 proves the scoped-access security model |
| Contract/e-signature | Excluded unless v0.9 evidence proves accepted Quote insufficient | No Contract work in v0.8 |
| Inventory and procurement | Excluded from v1.0 FSM scope | No inventory work in v0.8 |
| Full Customer Portal (account admin, messaging, self-service cases) | Excluded from v0.8 | Deferred to post-1.0 |
| Broad Cloud-to-Local deployment automation | Excluded from v0.8 | Agent-assisted Local deployment remains supported but not productized |
| Application fees, Destination Charges, wallets | Excluded from v0.8 Connect scope | Production Connect configuration remains v1.0 GA gate |

### 8.2 Customer journey acceptance fixture (Batch 2)

```text
operator issues Quote access grant
  → customer exchanges link token at /:locale/access
  → customer sees Quote (number, revision, amount, currency, validity)
  → customer accepts sent Quote via quote.accept (actor=customer)
  → operator converts Quote to Work Order, completes Work Order, issues Invoice
  → same root resolves Work Order status, service report, Invoice
  → customer starts exact-balance hosted Checkout via payment.request (actor=customer)
  → Connect webhook confirms Payment on merchant Connected Account
  → existing invoice.apply_payment effect allocates to Invoice
  → customer sees paid state
  → revoked grant immediately loses access on next request
```

Cross-tenant negative cases:
- invalid, expired, revoked, malformed, mismatched grants return same
  unavailable result
- cross-Workspace, cross-customer, cross-root, guessed-record access fails
- rate limits and same-origin mutation checks pass
- no internal field or provider reference appears in customer DTO

### 8.3 Stripe Connect sandbox acceptance fixture (Batch 2)

```text
Workspace A → Connected Account A (test mode)
  → merchant completes Stripe-managed onboarding
  → charges_enabled = true
  → customer pays via Direct Checkout on Connected Account A
  → Connect webhook confirms payment
  → refund executes on Connected Account A
  → Runory platform balance does not receive merchant gross receipts

Workspace B → Connected Account B (test mode)
  → independent onboarding, payment, refund
  → Workspace A cannot read, charge, refund, or replay Workspace B's account
  → wrong-mode, wrong-account, and unknown-account events fail safely
```

### 8.4 Workflow visibility acceptance fixture (Batch 3)

```text
linear workflow Run
  → steps project as pending → current → completed in order

approval workflow Run (approve path)

```

## 10. Key risks and mitigations

| Risk | Mitigation |
| --- | --- |
| `actions` in View config is currently dead data — renderers ignore it | Batch 1 must make `SchemaTable` and `SchemaForm` consume `ViewAction[]` from effective config, replacing hardcoded action builders |
| Three parallel `ViewConfig` types cause divergence | Consolidate into one shared type exported from `@runory/contracts` |
| `authorizeCommandActor` identity resolution assumes workspace membership | Customer branch must be entirely separate — resolve grant ID, not user ID |
| Stripe webhook is env-hardwired to one workspace | Connect webhook must resolve workspace from `event.account` + verified `livemode`, never from env or metadata |
| Payment outbox processor is synchronous | Customer checkout must not block on outbox; derive idempotency key server-side and return checkout URL |
| `payment_provider_account` has no Connect fields | Extend via `ALTER TABLE ADD COLUMN` with safe defaults; do not create a second account table |
