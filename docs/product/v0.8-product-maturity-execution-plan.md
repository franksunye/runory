## 1. Release decision

v0.8 matures the existing Reactive Repair product on its operator and
customer-facing surfaces. It does not productize Agent-generated official
Modules, Packs, or Templates.

```text
operator uses coherent Customer / Work Order / Invoice surfaces
→ customer receives secure, scoped access
→ customer reviews Quote, service outcome, and Invoice
→ customer accepts or pays through governed existing Commands
→ both sides see the same authoritative status
```

Engineering outcome:

> Reuse and tighten the existing View, Workflow, Manifest, Extension, and
> Command foundations; do not introduce parallel platform abstractions.

## 2. Current-reality audit

The earlier v0.8 proposal combined Agent contracts, MPT productization, Object
Views, a Workflow Builder, and Local deployment. That exceeds the structural
change budget and shifts work from the product into a factory for producing
more product.

The repository foundations already exist:

| Area | Existing evidence | v0.8 decision |
| --- | --- | --- |
| Views | `view_definitions`, metadata APIs, manifest views, extension view modifications | Type and converge the existing model; no second View framework |
| Workflow | Workflow V2 definitions, versions, instances, Work Items, editor and run inspection | Improve business-readable visibility; defer a canvas Builder |
| MPT | 61 manifests, validation, install/uninstall, migrations and compatibility checks | Maintain manually; defer Agent generation and public lifecycle |
| Agent change | MCP plus plan, preview, apply, verify/audit and rollback | Preserve and regression-test; do not expand into an implementation platform |
| Commands | machine-auditable Command Contracts and semantic Providers | Reuse for Quote acceptance and payment; no customer-only mutation path |

## 3. Binding scope

### 3.1 Product Surface convergence

- define one typed schema for the existing View Definition configuration;
- standardize field presentation, sort/filter, primary/secondary actions,
  permission, loading, empty, error, and partial-data states;
- reuse action descriptors across desktop and mobile where appropriate;
- prove the shared contract on Contact/Company, Work Order, and Invoice;
- retire page-specific configuration replaced by the shared contract;
- benchmark those surfaces against Twenty and Directus without copying their
  object or mutation models.

Minimum saved-view scope is role defaults and current-user filter, sort, and
visible-column preferences. Board layouts, arbitrary grouping, formulas, and a
general layout studio are excluded.

### 3.2 Minimum customer access

- provide an expiring, revocable, tenant-scoped access mechanism;
- bind access to the intended customer and allowed records;
- allow read-only access to relevant Quote, service report, Invoice, and
  payment status;
- reuse governed Quote acceptance and hosted-payment paths;
- audit issuance, access, acceptance, payment handoff, revocation, and failed
  authorization;
- implement explicit expired, revoked, completed, permission, and provider
  failure states;
- expose less data than internal Workspace records.

This is not a general Customer Portal. Account administration, customer-created
users, messaging, self-service cases, arbitrary sharing, and multi-organization
delegation are excluded.

### 3.3 Workflow clarity, not Workflow Builder

- map existing Workflow V2 to business-readable Overview and Run views;
- show current step, completed path, pending work, failure, retry, and audit
  context where the canonical journey needs it;
- keep Runtime definitions, versions, instances, and Work Items authoritative;
- record a later decision for Review, Configure, and canvas modes.

### 3.4 Existing Agent boundary preservation

- keep Agent operations on the same Command and permission paths as the UI;
- retain extension plan/preview/apply/audit/rollback regression coverage;
- do not add public MPT generation, marketplace, universal SDK, or
  Agent-assisted Local deployment work.

## 4. Explicit non-goals

- Agent-generated official Module/Pack/Template productization;
- public marketplace or general plugin ecosystem;
- full Workflow Builder or a second Workflow Runtime;
- general low-code Object/View studio;
- broad Cloud-to-Local deployment automation;
- full Customer Portal;
- Contract/e-signature unless v0.9 evidence proves accepted Quote insufficient;
- recurring service, project/installation, inventory, or accounting expansion;
- rebuilding existing foundations under new names.

## 5. Execution batches

### Batch 0 — Truth inventory and scope freeze

- produce current-versus-benchmark and Adopt/Adapt/Defer/Reject matrices;
- map each admitted item to an existing Runory model;
- record migration, compatibility, and five-area complexity impact;
- freeze reference-page and customer-journey acceptance fixtures.

Exit: roadmap documents agree, no parallel model is admitted, and every item
has acceptance evidence before implementation.

### Batch 1 — Existing View contract convergence

- typed View configuration and validation;
- shared query, presentation, and action contract;
- Contact/Company, Work Order, and Invoice reference implementations;
- bounded desktop/mobile consistency and saved preferences;
- migration from duplicated page configuration;
- unit, contract, permission, and visual regression evidence.

Exit: reference pages use the existing View model and governed actions remain
outside generic CRUD.

### Batch 2 — Minimum customer access

- scoped grant, expiry, revocation, and audit model;
- customer-facing Quote, service report, Invoice, and payment status;
- governed Quote acceptance and hosted-payment handoff;
- tenant, record-scope, enumeration, replay, stale-link, and revocation tests;
- responsive and accessible journey.

Exit: a customer completes the supported journey without a Workspace account,
without exposing another customer, Workspace, or internal field.

### Batch 3 — Workflow visibility and proportional refinement

- business-readable Overview and Run path over Workflow V2;
- current-step, work-item, error, retry, and audit visibility;
- written Review/Configure/canvas decision;
- remove accidental complexity found during acceptance.

Exit: users understand current state and next action without a new canvas or
workflow semantics.

### Batch 4 — v0.8 acceptance

- operator-to-customer Quote/report/Invoice/payment E2E;
- customer-access security matrix;
- Command, idempotency, concurrency, audit, revocation, and provider tests;
- three reference Product Surface benchmark reviews;
- full test, typecheck, docs, architecture, and performance gates;
- final proportionality review.

## 6. Version sequence

```text
v0.8  Product Surface convergence + minimum customer access
v0.9  Real-customer cohort, repeatable delivery, evidence-driven gap closure
v0.9.x  Minimum Contract only if repeated evidence proves Quote insufficient
v1.0  Reliability, supportability, compatibility, and GA freeze
post-1.0  Agent-generated official MPT, full Workflow Builder, broader ecosystem
```

Internal Agent assistance may continue; it is not a supported MPT-generation
product promise.

## 7. Stop rules

Remove an item from v0.8 when it does not improve the canonical journey,
duplicates an existing model, exists only for competitor parity, requires a
generic platform before three reference surfaces need it, primarily serves
hypothetical third-party authors, or lacks pre-implementation acceptance
evidence. The default for attractive benchmark features is Defer.

## 8. Definition of done

v0.8 is complete when operators use coherent shared surfaces for the three
reference objects; customers securely review bounded documents and complete
supported acceptance/payment; Workflow state is understandable; all surfaces
share authoritative state and governed Commands; no MPT generation, full
portal, full Builder, Contract, or second commercial shape was required; and
all release and proportionality gates pass.
