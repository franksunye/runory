## 1. Purpose and authority

This document is the binding implementation specification for v0.8. The
execution plan defines scope, sequence, and release gates; this specification
defines the exact contracts that implementation must preserve or add.

If a code change requires a second View model, Workflow Runtime, customer-only
business mutation path, or broader portal/MPT platform, stop and amend the
specification through an explicit architecture decision before implementation.

## 2. Current implementation baseline

v0.8 extends these existing foundations:

| Foundation | Current implementation | v0.8 treatment |
| --- | --- | --- |
| View metadata | `view_definitions`; `ViewDefinition.config` is currently `Record<string, unknown>`; list/form manifests; `SchemaTable` and `SchemaForm` | add typed validation and normalized composition; retain table and identity |
| Workspace Extensions | field and view modifications with plan/preview/apply/audit/rollback | retain; validate modifications against the typed View contract |
| Workflow | Workflow V2 definitions, immutable versions, pinned instances, events and Work Items | add pure Overview/Run projections; no new Runtime or canvas |
| Command Runtime | `CommandActor`, persisted Command Contracts, permission/tenant authorization, idempotency, concurrency, audit and events | add a narrowly authorized `customer` actor type |
| Quote | governed `quote.accept`, immutable accepted state and explicit revision | reuse the Command; no public direct update |
| Invoice/Payment | Invoice balance and allocation truth, `payment.request`, hosted Checkout and provider-confirmed events | reuse Commands/providers; add merchant-owned Stripe Connect Direct Charges; public flow derives all financial input server-side |
| MPT | existing manifests, installer, migrations, compatibility and extension boundaries | regression-test only; no Agent-generated official MPT productization |

## 3. Binding invariants

1. `view_definitions` remains the only Product View definition model.
2. Workflow V2 remains the only business Workflow definition and execution
   model.
3. A public customer never becomes or impersonates a Workspace member.
4. A raw customer-access token is never persisted, logged, audited, or placed
   in a query string.
5. Customer-visible records are resolved from one explicit journey root and a
   customer subject; arbitrary object queries are prohibited.
6. Customer mutations execute existing named Commands with a server-derived
   actor, input, expected version, and idempotency key.
7. Generic CRUD remains unavailable to the customer-access surface.
8. Quote, Invoice, Payment, refund, and allocation authority remain in their
   existing Modules and Providers. Stripe payment objects and gross merchant
   receipts belong to the Workspace merchant's Connected Account.
9. Revocation takes effect on the next request; cached protected responses are
   prohibited.
10. Every admitted schema and API change is tenant-scoped and backward
    compatible with installed v0.7 Workspaces.

## 4. Typed View Definition contract

### 4.1 Contract ownership

Add the schemas to `@runory/contracts` and export inferred TypeScript types.
Platform Core parses stored and manifest configuration through these schemas
before returning it to applications.

The existing `ViewDefinition` shape and database table remain unchanged. Only
`config` changes from unvalidated `Record<string, unknown>` to a parsed union.

### 4.2 Shared types

```ts
type ViewAction = {
  key: string;
  label?: string;
  kind: "navigate" | "command";
  permission?: string;
  command?: string;
  tone?: "primary" | "secondary" | "danger";
};

type ExactFilter = {
  field: string;
  operator: "eq";
  value: string | number | boolean;
};

type SortDefinition = {
  field: string;
  direction: "asc" | "desc";
};

type ListViewPreferenceOverlay = {
  visibleFields?: string[];
  filters?: ExactFilter[];
  sort?: SortDefinition;
  pageSize?: 10 | 20 | 50 | 100;
};
```

v0.8 intentionally supports exact filters only because the current record
query contract supports exact-match relation/module fields. A generic query
DSL is not admitted.

### 4.3 List View configuration

```ts
type ListViewConfigV1 = {
  schemaVersion: "1.0";
  columns: Array<{
    field: string;
    label?: string;
    width?: "sm" | "md" | "lg";
  }>;
  actions: ViewAction[];
  defaultSort?: SortDefinition;
  defaultFilters?: ExactFilter[];
  pageSize: 10 | 20 | 50 | 100;
  workspaceRoleDefaults?: Partial<
    Record<"admin" | "member" | "viewer", ListViewPreferenceOverlay>
  >;
  emptyState?: {
    title?: string;
    description?: string;
    actionKey?: string;
  };
};
```

Validation rules:

- every column, sort field, and filter field exists in effective fields;
- duplicate columns and action keys are rejected;
- command actions reference a discovered Command and declared permission;
- `danger` is allowed only for a Command action;
- generic `create`, `update`, or `delete` is never synthesized for governed
  financial or lifecycle objects;
- page size outside the enum is rejected, not silently coerced.

`field` values are canonical effective-metadata field keys. They remain stable
across installation and Workspace migration and do not expose database row IDs
or reference-platform metadata IDs.

### 4.4 Form/record configuration

```ts
type FormViewConfigV1 = {
  schemaVersion: "1.0";
  sections: Array<{
    key: string;
    title: string;
    fields: Array<{ field: string; required?: boolean }>;
  }>;
  actions: ViewAction[];
};
```

The first migration parser accepts current legacy configuration:

- string actions such as `create` and `view` normalize to action descriptors;
- missing `schemaVersion` normalizes to `1.0` after successful validation;
- form sections without keys receive a deterministic key derived from the
  view key and section position during installation/upgrade;
- invalid effective configuration fails Catalog validation or Workspace
  diagnostics; applications do not guess.

### 4.5 Composition order

```text
installed Module View
→ validated Workspace Extension modifications
→ role default from effective View configuration
→ current-user preference
→ permission and governed-action filtering
→ rendered surface
```

Later layers may hide/reorder visible fields or apply allowed exact filters and
sort. They may not add fields, Commands, or permissions unavailable in an
earlier layer.

`workspaceRoleDefaults` is the only role-default mechanism in v0.8. Resolution
uses the caller's effective Workspace role. Permission-group/business-role
presets, editable shared presets, and role-preset CRUD are deferred because
they introduce precedence and ownership semantics that the reference journeys
do not require. Changing a role default requires the existing governed Module
or Workspace Extension path; changing a personal preference never mutates it.

### 4.6 User View preferences

Add the next available Runtime migration with this table:

```sql
CREATE TABLE {{RUNORY_RUNTIME_TABLE_PREFIX}}view_preferences (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  view_definition_id TEXT NOT NULL,
  visible_fields_json TEXT NOT NULL,
  filters_json TEXT NOT NULL,
  sort_json TEXT,
  page_size INTEGER,
  version INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(workspace_id, user_id, view_definition_id)
);
```

Preferences implement `ListViewPreferenceOverlay` and contain only visible
field keys, exact filters, one sort, and an optional allowed page size. Query
state (filters and sort) remains distinct from presentation state (visible
fields and page size). Preferences do not contain actions, permissions,
arbitrary SQL, layout code, or customer access configuration.

Authenticated API:

```text
GET /api/workspaces/:workspaceId/views/:viewId/preference
PUT /api/workspaces/:workspaceId/views/:viewId/preference
```

`PUT` requires the current preference version when one exists. Validation uses
the effective View and fields before persistence. A user can access only their
own preference.

### 4.7 Reference surfaces

The typed contract must be proven on:

- Company and Contact as the unified customer subject surface;
- Work Order as the operational aggregate;
- Invoice as the governed commercial aggregate.

Page-specific props may remain for titles and routes. Columns, sections,
actions, defaults, and UI-state behavior must come from the effective View
contract.

## 5. Customer Access Platform Service

### 5.1 Ownership decision

Create the Platform Service contract `runory.customer-access`. It owns access
grants and public authorization only. It does not own Quote, Work Order,
service report, Invoice, Payment, customer identity, email delivery, or files.

Required permissions:

```text
customer_access.read
customer_access.manage
```

Required Commands:

```text
customer_access.issue
customer_access.revoke
```

Both Commands are idempotent, audited, tenant-scoped, and allowed only to
`user`, `api_key`, `system`, and `agent` actors that pass normal Workspace
authorization. Issue is a create operation; revoke requires expected version.

### 5.2 Grant persistence

Add the next available Runtime migration:

```sql
CREATE TABLE {{RUNORY_RUNTIME_TABLE_PREFIX}}customer_access_grants (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL,
  subject_type TEXT NOT NULL CHECK(subject_type IN ('contact', 'company')),
  subject_id TEXT NOT NULL,
  root_object_type TEXT NOT NULL CHECK(root_object_type IN ('quote', 'work_order')),
  root_record_id TEXT NOT NULL,
  capabilities_json TEXT NOT NULL,
  token_hash TEXT NOT NULL UNIQUE,
  expires_at TEXT NOT NULL,
  first_accessed_at TEXT,
  last_accessed_at TEXT,
  revoked_at TEXT,
  revoked_by TEXT,
  created_by TEXT NOT NULL,
  aggregate_version INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(workspace_id, id)
);
```

Indexes are required on `(workspace_id, subject_type, subject_id)`,
`(workspace_id, root_object_type, root_record_id)`, and `token_hash`.

Allowed capabilities are a closed enum:

```text
quote.view
quote.accept
work_order.view_status
service_report.view
invoice.view
invoice.pay
payment.view_status
```

An issue request may select only capabilities valid for its root and current
linked records. Unknown capabilities are rejected.

### 5.3 Journey resolution

The resolver always starts with `(workspace_id, root_object_type,
root_record_id)` and verifies subject ownership before returning data.

For a Quote root:

```text
Quote
→ Quote.company_id or Quote.contact_id must match grant subject
→ Quote.work_order_id, if present
→ Work Order service reports and Invoice
→ Invoice payment requests, Payments and allocation-derived status
```

For a Work Order root:

```text
Work Order
→ WorkOrder.company_id or WorkOrder.contact_id must match grant subject
→ source Quote only when source_type == quote and source_id is valid
→ service reports and Invoice
→ Invoice payment requests, Payments and allocation-derived status
```

No generic relation traversal is allowed. A missing or mismatched link returns
not found to the public caller and records a safe failed-authorization event.

### 5.4 Customer-visible field allowlists

The service returns explicit DTOs, never raw business rows.

```text
Quote:
  id, quoteNumber, title, status, currency, subtotal, discountTotal,
  taxTotal, grandTotal, validUntil, terms, revisionNumber, acceptedAt, lines

Work Order status:
  id, number, title, status, scheduledStart, scheduledEnd, completedAt

Service report:
  id, summary, resolution, completedAt

Invoice:
  id, invoiceNumber, status, currency, totalMinor, amountPaidMinor,
  balanceDueMinor, issuedAt, dueAt, paidAt, memo, lines

Payment status:
  requestStatus, paymentStatus, amountMinor, refundedAmountMinor, currency
```

Internal notes, ownership, assignment, provider account/reference, failure
payloads, audit internals, extension fields, raw signature data, and attachment
storage identifiers are excluded. Customer-visible attachments require a
future explicit publication model and are not part of v0.8.

## 6. Token and session protocol

### 6.1 Link creation

- generate 32 random bytes with a cryptographically secure generator;
- encode as base64url;
- persist only `SHA-256(rawToken)`;
- return the raw token once from `customer_access.issue`;
- generate links as `/:locale/access#token=<rawToken>` so the token is not sent
  in HTTP requests, server logs, analytics, or referrers;
- do not place the raw token in audit or Domain Event payloads.

Maximum grant lifetime is 30 days. The issuer may choose a shorter expiry.

### 6.2 Exchange

```text
POST /api/customer-access/exchange
body: { token: string }
```

On success, the server:

1. hashes and looks up the token;
2. verifies expiry, revocation, root, subject, and Workspace status;
3. creates a signed, opaque customer-access session cookie containing grant ID
   and issued/expiry times;
4. bounds cookie expiry to grant expiry;
5. updates first/last access timestamps and audit;
6. returns no raw business data.

Cookie requirements:

```text
HttpOnly
Secure in non-local environments
SameSite=Lax
Path=/
signed with a dedicated CUSTOMER_ACCESS_SESSION_SECRET
```

The raw link token remains a bearer credential until grant expiry or
revocation; it may be exchanged again. Revocation is checked on every protected
request.

### 6.3 Protected response policy

Every customer-access page and API response sets:

```text
Cache-Control: private, no-store
Referrer-Policy: no-referrer
X-Robots-Tag: noindex, nofollow
```

Mutation routes also require same-origin validation. Exchange and mutation
attempts are rate-limited by IP plus token/grant fingerprint. Public errors do
not distinguish missing, expired, revoked, or mismatched records.

## 7. Customer Command authorization

### 7.1 Actor contract

Extend `commandActorTypeSchema`, `CommandActor`, persisted Contract validation,
events, and audit actor types with:

```ts
type CommandActorType = "user" | "api_key" | "system" | "agent" | "customer";
```

For a customer actor, `actor.id` is the server-resolved grant ID. The client
cannot submit actor type or actor ID.

### 7.2 Authorization branch

`authorizeCommandActor` must not resolve a customer as a Workspace member. It
delegates to `authorizeCustomerCommandActor`, which verifies:

- active, unexpired grant in the same Workspace;
- Command explicitly allows `customer`;
- grant capability permits the Command;
- Command aggregate is reachable from the grant root;
- aggregate customer subject matches the grant subject;
- public route supplied no unapproved business input.

Only these existing Commands admit `customer` in v0.8:

| Command | Grant capability | Server-derived constraints |
| --- | --- | --- |
| `quote.accept` | `quote.accept` | exact reachable Quote; state `sent`; expected version from current Quote; no client actor/input |
| `payment.request` | `invoice.pay` | exact reachable issued/partially-paid Invoice; current balance and currency; purpose `final`; customer contact and return URLs derived server-side |

Provider confirmation and refunds remain `system`/authorized internal actions.
Customers cannot issue/void Invoices, request refunds, change Work Orders, or
invoke generic record mutations.

### 7.3 Idempotency

The public server derives stable keys:

```text
customer-access:<grantId>:quote.accept:<quoteId>
customer-access:<grantId>:invoice.checkout:<invoiceId>:<balanceMinor>
```

If an eligible open Payment Request already exists for the Invoice, the
checkout route returns/reprocesses that request rather than creating another.
Changed balance produces a new key only after the prior request is no longer
open.

## 8. API contract

### 8.1 Authenticated Workspace APIs

```text
GET  /api/workspaces/:workspaceId/customer-access/grants
POST /api/workspaces/:workspaceId/customer-access/grants
POST /api/workspaces/:workspaceId/customer-access/grants/:grantId/revoke
```

Issue body:

```ts
{
  subjectType: "contact" | "company";
  subjectId: string;
  rootObjectType: "quote" | "work_order";
  rootRecordId: string;
  capabilities: CustomerAccessCapability[];
  expiresAt: string;
}
```

Issue response returns grant metadata plus `accessUrl` exactly once. List never
returns token or hash. Revoke requires `expectedVersion` and is idempotent.

### 8.2 Public APIs

```text
POST /api/customer-access/exchange
GET  /api/customer-access/context
POST /api/customer-access/quotes/:quoteId/accept
POST /api/customer-access/invoices/:invoiceId/checkout
POST /api/customer-access/session/logout
```

`GET context` returns one customer-safe journey DTO:

```ts
{
  grant: { id: string; expiresAt: string; capabilities: string[] };
  workspace: { name: string };
  customer: { displayName: string };
  quote?: CustomerQuoteDto;
  workOrder?: CustomerWorkOrderStatusDto;
  serviceReports: CustomerServiceReportDto[];
  invoice?: CustomerInvoiceDto;
  payment?: CustomerPaymentStatusDto;
  availableActions: Array<"quote.accept" | "invoice.pay">;
}
```

The checkout response is `{ checkoutUrl: httpsUrl }`. It never accepts amount,
currency, purpose, source, provider account, success URL, or cancel URL from
the browser.

All APIs use the repository's standard structured error envelope internally;
public authorization failures collapse to one safe unavailable response.

## 9. Stripe Connect Direct-Charge contract

### 9.1 Product and funds-flow boundary

Stripe Connect is part of the existing `runory.payment` provider boundary. It
does not introduce another Payment aggregate, payment ledger, Invoice model, or
customer checkout path.

v0.8 uses Stripe Connect Direct Charges:

```text
Workspace merchant
→ Stripe-managed Connected Account onboarding
→ Runory stores the Workspace/account mapping and readiness projection
→ Checkout Session is created in the Connected Account context
→ customer pays the Workspace merchant
→ Connect webhook confirms the authoritative outcome
→ existing Payment Commands allocate the payment to the Invoice
```

Destination Charges, Separate Charges and Transfers, application fees, stored
balance, wallets, Runory-held gross merchant receipts, and custom KYC collection
are prohibited in v0.8. Account configuration uses current Stripe controller/
responsibility properties rather than relying on legacy account-type labels.

The default launch configuration gives the merchant access to the full Stripe
Dashboard and assigns payment fees, negative-balance responsibility, and KYC
requirement collection to Stripe/the Connected Account where Stripe supports
that configuration. If a launch country cannot support that responsibility
model, implementation stops for an explicit product, legal, finance, and
architecture decision; it must not silently move those responsibilities to
Runory.

### 9.2 Provider-account persistence

Upgrade `runory.payment` through its next versioned Module migration. The
existing `payment_provider_account` row remains authoritative. For Stripe,
`provider_account_ref` stores the `acct_...` Connected Account identifier; do
not add a second account-ID mapping.

Add these fields to that object/table:

```text
account_configuration_version TEXT
onboarding_status             not_started | in_progress | complete |
                              restricted | disconnected
details_submitted             boolean
charges_enabled               boolean
payouts_enabled               boolean
requirements_status           pending | due | past_due | disabled | clear
requirements_json             allowlisted requirement codes only; no KYC PII
last_synced_at                 timestamp
disconnected_at               timestamp | null
aggregate_version             integer
```

There is at most one non-disconnected Stripe mapping per Workspace and mode.
Test and live mappings, webhook secrets, idempotency keys, and provider events
must never cross modes. Stripe secret keys and webhook signing secrets remain
deployment secrets and are never stored in Workspace business records.

### 9.3 Governed account lifecycle

Add these named Commands and persisted Command Contracts:

| Command | Allowed actors | Permission | Result |
| --- | --- | --- | --- |
| `payment.connect.start` | `user`, `api_key` | `payment.configure` | create/resume Stripe-managed onboarding and return a short-lived onboarding URL |
| `payment.connect.sync` | `system` | system boundary | refresh allowlisted account readiness from Stripe or verified `account.updated` |
| `payment.connect.disconnect` | `user`, `api_key`, `system` | `payment.configure` for non-system | disable new payment/refund requests while retaining history |

`start` is idempotent for the active Workspace/mode mapping. `disconnect`
requires expected version and never deletes Payment, Refund, provider-event, or
audit history. Replacing an account is allowed only after explicit disconnect
and creates a new provider-account row.

Authenticated Workspace API:

```text
GET  /api/workspaces/:workspaceId/integrations/stripe/connect/account
POST /api/workspaces/:workspaceId/integrations/stripe/connect/onboarding
POST /api/workspaces/:workspaceId/integrations/stripe/connect/disconnect
GET  /api/workspaces/:workspaceId/integrations/stripe/connect/return
```

The return route is non-authoritative: it triggers/reads a server-side account
sync and redirects to the account status surface. It does not mark onboarding
complete from browser parameters.

### 9.4 Direct Checkout, retrieval, and refund

For every Stripe Checkout Session, PaymentIntent retrieval, refund, and
reconciliation request, the Stripe adapter passes the resolved Connected
Account context (`Stripe-Account` / SDK request option) from
`payment_provider_account.provider_account_ref`.

The adapter rejects execution unless:

- provider is Stripe and mode matches the configured Stripe key;
- onboarding is complete and `charges_enabled` is true;
- the Payment Request, provider account, Workspace, amount, and currency match;
- the connected account mapping is active and not disconnected/restricted.

Customer checkout still executes the existing `payment.request` Command.
Amounts, currency, Invoice, provider account, return URLs, and idempotency keys
are derived server-side. Refunds execute the existing governed refund path in
the same Connected Account that owns the PaymentIntent.

### 9.5 Connect webhook

Add a dedicated endpoint and signing secret, separate from Runory SaaS Billing
and any legacy single-account merchant webhook:

```text
POST /api/integrations/stripe/connect-webhook
```

After signature verification, resolve the Workspace only from the event's
top-level connected-account ID and verified `livemode`; never accept a
Workspace ID from redirects, metadata, or an unsigned body as authority.
Provider-event uniqueness is scoped to provider, mode, connected account, and
event ID.

Required event families for v0.8 are `account.updated`, Checkout completion/
asynchronous success/failure, PaymentIntent success/failure/processing, Charge
refund updates, and dispute creation/update/closure. Events may arrive more
than once or out of order; they must not regress terminal business state.

### 9.6 Operator surface and release boundary

The Workspace payment settings surface shows onboarding status,
`charges_enabled`, `payouts_enabled`, allowlisted outstanding requirements,
mode, last synchronization, disconnect action, and safe diagnostics. Payout,
balance, payment, refund, and dispute detail may link to Stripe-hosted or
approved embedded surfaces; v0.8 does not recreate the Stripe Dashboard.

v0.8 acceptance requires two independent sandbox merchants, each completing
onboarding, Direct Checkout, provider-confirmed allocation, and refund, plus
cross-Workspace and wrong-mode denial. Production Connect configuration,
legal/finance/operations approval, and a limited approved live-money drill
remain v1.0 GA release gates.

Stripe implementation authority:

- [Create direct charges](https://docs.stripe.com/connect/direct-charges)
- [Connect webhooks](https://docs.stripe.com/connect/webhooks)
- [Connected account configuration](https://docs.stripe.com/connect/accounts-v2/connected-account-configuration)

## 10. Customer UI contract

Public route:

```text
/:locale/access
```

States:

1. exchanging link;
2. unavailable/expired/revoked;
3. Quote awaiting acceptance;
4. accepted Quote/job status;
5. service completed/report available;
6. Invoice outstanding/partially paid;
7. redirecting to hosted Checkout;
8. payment processing/paid/refunded;
9. provider return/cancel/failure.

The page is responsive, keyboard-operable, screen-reader labelled, and uses
the existing locale system. It has no Workspace navigation, generic object
links, internal IDs in copy, customer account settings, messaging, or support
case creation.

Acceptance confirmation displays Quote number, revision, amount, currency, and
validity before action. Payment displays Invoice number, current balance, and
currency before redirecting to hosted Checkout.

## 11. Workflow Overview and Run projection

### 11.1 No persistence change

Workflow definitions, versions, instances, Work Items, and events remain
unchanged. Add pure projection functions and types in Platform Core/contracts:

```ts
type WorkflowOverview = {
  workflowKey: string;
  name: string;
  targetObject: string;
  versionNumber: number;
  steps: Array<{
    id: string;
    kind: WorkflowStepKind;
    label: string;
    next: string[];
  }>;
};

type WorkflowRunProjection = {
  instanceId: string;
  status: "running" | "completed" | "returned" | "cancelled";
  currentStepId: string | null;
  startedAt: string;
  completedAt: string | null;
  steps: Array<{
    id: string;
    state: "pending" | "current" | "completed" | "cancelled";
    workItemStatus?: string;
    occurredAt?: string;
    outcome?: "approved" | "rejected" | "returned" | "cancelled";
  }>;
  nextAction?: { kind: string; workItemId?: string };
};
```

`next` contains `step.next` plus approval `onApprove`/`onReject` targets. v0.8
does not invent conditions, loops, compensation nodes, or layout coordinates
that Workflow V2 does not own.

Projection status and step history come only from the pinned definition
version, instance, Work Items, and ordered Workflow events. Workflow V2 does
not currently own a failed instance state, retry policy, execution attempt, or
log stream. Therefore v0.8 does not infer failure/retry data from returned Work
Items, repeated events, audit entries, or Command errors. Those capabilities
require a later Runtime contract before they can appear in a Run projection.

### 11.2 API compatibility

Existing Workflow endpoints remain. Add projections without removing current
fields:

```text
GET /api/workspaces/:workspaceId/workflows/definitions
  + overview

GET /api/workspaces/:workspaceId/workflows/instances/:instanceId
  + runProjection
```

Projection is permission-filtered through existing Workspace access. The
customer surface does not expose general Workflow definitions or events.

### 11.3 UI scope

- Overview: business-readable step sequence and branches;
- Run: completed/current/pending path, active Work Item, approval outcome, and
  returned/cancelled event context;
- no drag/drop, canvas persistence, Inspector, draft editor replacement,
  visual Diff, Agent-generated workflow mutation, retry-attempt explorer, or
  general log/asset browser.

## 12. Audit and event contract

Required audit actions:

```text
customer_access.issue
customer_access.exchange
customer_access.access_denied
customer_access.revoke
customer_access.logout
quote.accept                 actor_type=customer
payment.request              actor_type=customer
payment.connect.start
payment.connect.sync
payment.connect.disconnect
```

Audit and events may store grant ID, Workspace ID, aggregate type/ID, action,
result, request ID, and timestamps. They must not store raw tokens, cookies,
Checkout URLs, email content, provider payloads, or internal failure secrets.

Access-denied audit is sampled/rate-limited to avoid an attacker creating an
unbounded audit stream.

## 13. Migration and compatibility

1. Use the next available numbered migrations for customer grants and View
   preferences; do not edit released migrations.
2. Existing View rows and manifests remain readable through the legacy
   normalization adapter.
3. Catalog validation requires typed View output for newly published or
   upgraded artifacts after the v0.8 compatibility boundary.
4. Installed v0.7 Workspaces receive Platform Service Contract sync and schema
   migrations without reinstalling FSM modules.
5. Quote and Payment Module versions increment because their Command Contracts
   add the `customer` actor; Pack/template dependency ranges and fixtures update
   together.
6. Workspace Contract snapshots upgrade through the existing governed upgrade
   and diagnostics path.
7. Rollback may disable customer-access routes and revoke grants, but it must
   retain audit/history and must not roll back Quote acceptance or Payment
   outcomes already committed.
8. The Payment Module upgrade extends `payment_provider_account`; it does not
   repurpose the Runory SaaS Billing Stripe account or event ledger.

## 14. Required test matrix

### 14.1 View contract

- legacy list/form config normalizes deterministically;
- invalid fields/actions/page size fail validation;
- extension modifications compose once and cannot add unauthorized actions;
- user preference is tenant/user/view scoped and optimistic-lock safe;
- governed financial objects never receive generic mutation actions;
- Company/Contact, Work Order, and Invoice render from effective definitions.

### 14.2 Customer access security

- raw token is absent from DB, logs, audit, URL query, referrer, and response
  after exchange;
- invalid, expired, revoked, malformed and mismatched grants return the same
  public unavailable result;
- revocation blocks an already issued cookie on its next request;
- cross-Workspace, cross-customer, cross-root, guessed-record, and wrong-field
  access fail;
- rate limits and same-origin mutation checks pass;
- no internal field or provider reference appears in DTO snapshots.

### 14.3 Customer Commands

- customer cannot execute a Contract that omits `customer` actor;
- customer grant capability and aggregate/root checks are both required;
- duplicate Quote acceptance returns the same outcome;
- stale expected version returns conflict without state change;
- checkout derives exact Invoice balance/currency and reuses an open request;
- overpayment, void/paid Invoice, expired grant, provider mismatch, and wrong
  Invoice fail;
- provider webhook still owns Payment success and Invoice allocation.

### 14.4 Workflow projection

- linear, approval approve/reject, active Work Item, completed, returned, and
  cancelled Runs project deterministically;
- projection does not fabricate failed/retry/attempt/log state absent from
  Workflow V2;
- instances remain pinned to their immutable definition version;
- projection performs no writes and exposes no unauthorized payload fields.

### 14.5 End to end

```text
operator issues Quote access
→ customer exchanges link and accepts sent Quote
→ operator converts Quote, completes Work Order and issues Invoice
→ same root resolves job/report/Invoice
→ customer starts exact-balance hosted Checkout
→ signed provider event allocates Payment
→ customer sees paid state
→ revoked grant immediately loses access
```

The E2E also runs cross-tenant negative cases and duplicate/reordered provider
events.

### 14.6 Stripe Connect

- two Workspaces map to different sandbox Connected Accounts and modes;
- incomplete, restricted, disabled, disconnected, and stale account states
  reject new Checkout/refund execution;
- Checkout, PaymentIntent retrieval, refund, and reconciliation always use the
  owning Connected Account context;
- Connect webhook signature, account, mode, amount, currency, and provider
  object mismatches fail safely;
- duplicate and reordered account/payment/refund/dispute events do not regress
  authoritative state;
- one Workspace cannot onboard, read, charge, refund, replay, or reconcile the
  other Workspace's account;
- Runory platform Payment/Checkout objects and balance do not receive merchant
  gross receipts in the acceptance fixtures.
