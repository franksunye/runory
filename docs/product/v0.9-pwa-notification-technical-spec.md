## 1. Product decision

v0.9.2 adds user-consented Web Push to the existing Runory PWA so important
FSM events can reach a person while Runory is closed or in the background.
The browser and installed PWA use the operating system's notification surface;
this does not require a native iOS or Android application.

The capability serves two principal classes:

1. **Runory system users** — workspace members such as technicians,
   dispatchers, reviewers, and owners;
2. **external users** — authenticated customer-access principals introduced in
   v0.8, within the Workspace and resource scope of their active access grant.

This is a completion of the existing mobile PWA and notification/outbox
foundations, not a new commercial shape or a second messaging platform.

## 2. P0 value and events

Push is reserved for events where delayed awareness can block service or
payment. The initial event set is deliberately small.

| Audience | P0 event | Default deep link |
| --- | --- | --- |
| System user | work assigned or reassigned | assigned Work Item / Visit |
| System user | Visit time changed or cancelled | Visit detail |
| System user | submitted work returned for correction | returned Work Item |
| System user | approval/review work becomes actionable | My Work item |
| External user | Quote is ready or changes acceptance state | scoped Quote access |
| External user | Invoice/payment request is ready or payment state changes | scoped Invoice/payment access |
| External user | Visit schedule or service completion changes | scoped customer-access page |

P0 excludes marketing broadcasts, arbitrary admin-authored bulk push, chat,
two-way messaging, generic workflow-builder push actions, and high-frequency
operational telemetry.

## 3. Reference decision: StockWise/ZISO

The local StockWise implementation proves the browser path and provides useful
production lessons:

| StockWise evidence | Runory decision |
| --- | --- |
| VAPID subscription through `PushManager` | **Adopt** the standards-based Web Push mechanism. |
| Explicit permission and enable/disable UI | **Adopt**; permission is requested only after a user gesture. |
| `push` and `notificationclick` Service Worker handlers | **Adopt**, with Runory-safe relative routes and authorization on open. |
| stale subscription rebuild and 404/410 cleanup | **Adopt** subscription reconciliation and expiry cleanup. |
| local notification test and remote end-to-end test | **Adopt** both diagnostic levels. |
| notification preferences and delivery history | **Adapt** to Runory principals, workspaces, notification types, and existing delivery model. |
| standalone internal `/notify` endpoint | **Reject** for Runory; dispatch must use the existing Notification → Message Delivery → Outbox path. |
| global broadcast when no target is supplied | **Reject** for v0.9; every push resolves an authorized recipient set. |
| product-specific cache and identity recovery behavior | **Reject**; retain Runory's conservative PWA cache and same-origin session policy. |

Runory should reuse the lessons, not copy the StockWise code or its product
assumptions.

## 4. One notification model

Web Push is a delivery channel of the existing communication domain:

```text
governed business event / timer / automation
→ Notification intent
→ Message
→ Message Delivery(channel = web, provider = web-push)
→ transactional Outbox message(message_delivery.web_push)
→ Web Push provider
→ Service Worker
→ OS notification
→ authenticated, permission-checked deep link
```

The business command and its outbox intent MUST commit atomically where the
notification is part of a state transition. A successful Web Push provider
request means `accepted`, not proven human delivery or reading. Runory MUST NOT
claim stronger delivery semantics than Web Push provides.

Do not add a second notification log, retry engine, broadcast API, or
provider-specific business state.

## 5. Principal and subscription contract

One person may subscribe multiple devices. Each subscription belongs to one
authenticated principal within one Workspace.

```text
PushSubscription
  id
  workspace_id
  principal_type       workspace_membership | customer_access_grant
  principal_id         membership ID or active customer-access grant ID
  endpoint_hash        stable uniqueness and lookup; endpoint is never logged
  endpoint             provider endpoint, treated as sensitive
  p256dh               subscription public key, treated as sensitive
  auth                 subscription auth secret, treated as sensitive
  user_agent_summary   bounded diagnostics only
  status               active | disabled | expired | revoked
  created_at
  last_verified_at
  last_accepted_at
  last_error_code
```

Required invariants:

- endpoint and key material are sensitive: exclude them from logs, audit
  payloads, exports, support bundles, and ordinary Admin APIs; rely on managed
  database encryption at rest and access control for v0.9 rather than creating
  a new application-level vault solely for Web Push;
- uniqueness prevents duplicate active registration for the same endpoint and
  principal;
- APIs derive principal and Workspace from the authenticated session, never
  from caller-supplied identity fields;
- customer-access subscriptions cannot outlive their bounded root-record grant;
  v0.9 does not silently convert that grant into a durable customer account;
- explicit logout or notification disable deactivates the relevant device
  subscription server-side;
- re-enable reconciles or replaces stale browser subscriptions;
- provider 404/410 responses mark the subscription expired and stop retries;
- account/member removal and Workspace deletion revoke associated subscriptions.

## 6. Preferences and consent

The P0 preference model contains:

```text
global enabled
work_assignment enabled
schedule_change enabled
work_returned enabled
approval_ready enabled
customer_document enabled
payment_status enabled
service_status enabled
```

Only categories applicable to the current principal are shown. Defaults may be
enabled in product policy, but browser permission and subscription creation are
always explicit opt-in. Runory MUST NOT prompt for browser permission on first
page load.

Denied, unsupported, not-installed-on-required-platform, and server-not-
configured states receive clear guidance rather than repeated prompts. A user
can disable one device without disabling their other devices.

## 7. Browser and Service Worker contract

### 7.1 One installable Runory PWA

The current manifest starts at `/m` and the Service Worker is registered only
for `/m/`, while external customer access lives at `/{locale}/access`. That
boundary cannot truthfully support installed-PWA notification acceptance for
both principal classes.

v0.9 therefore promotes the existing field PWA into one product-level Runory
PWA:

```text
manifest id              /runory
manifest start_url       /app
manifest scope           /
Service Worker script    /sw.js
Service Worker scope     /

/app launch resolver
  workspace session only       → /m or last safe mobile workspace
  customer-access session only → /{locale}/access
  both/ambiguous               → explicit principal/surface chooser
  neither                       → sign-in/access-token entry
```

This changes installation and routing scope, not business ownership. `/m` stays
the system-user field shell and `/{locale}/access` stays the external-user
surface. They continue to use their existing sessions, permissions, grants,
Commands, and APIs. No second PWA, second Service Worker, or shared principal is
introduced.

Expanding Service Worker control to `/` is permitted only with a network-only
default and the existing explicit safe-static allowlist. It does not authorize
caching desktop, customer-access, authenticated, API, RSC, document, or
business-data responses.

### 7.2 Push behavior

The existing `/sw.js` remains the only Service Worker. v0.9 extends it with:

- `push`: parse a versioned, size-bounded payload and display one visible
  notification;
- `notificationclick`: close the notification, focus a matching same-origin
  client or open the safe relative route;
- optional badge set/clear when the platform supports it;
- subscription reconciliation when the application resumes;
- safe handling of malformed payloads without showing raw content.

Payload shape:

```json
{
  "version": 1,
  "notificationId": "ntf_...",
  "title": "Work needs your attention",
  "body": "Open Runory to review the update.",
  "route": "/m/w/{workspaceId}/work/{workItemId}",
  "tag": "work-item:{workItemId}"
}
```

`route` MUST be a validated same-origin relative route from an allowlisted
Runory surface. The Service Worker MUST reject absolute/cross-origin URLs.
Opening a notification never bypasses session, Workspace, grant, object, or
record authorization.

The existing cache contract remains unchanged apart from registration scope:
push support MUST NOT cause API,
authenticated HTML, RSC data, customer files, or business payloads to enter a
Service Worker cache.

## 8. Privacy and content rules

OS notifications can appear on a locked or shared device. Default titles and
bodies therefore contain no customer name, phone, address, health/safety notes,
payment amount, invoice details, evidence, or free-form internal comments.

The notification carries only enough context to invite an authenticated open.
Detailed content is fetched after authorization. Workspace-level policy may
later allow richer previews, but that is not part of v0.9.

All subscribe, unsubscribe, revoke, preference-change, test-send, accepted,
failed, and expired outcomes are auditable without logging endpoint URLs or
encryption keys.

## 9. API boundary

Exact route naming may follow repository conventions, but the capability must
provide these authenticated operations:

```http
GET    push capability/configuration status
GET    current-device subscription status and preferences
POST   subscribe current device
DELETE unsubscribe current device
PATCH  notification preferences
POST   local display test (client-side capability diagnostic)
POST   remote push test (server → provider → device diagnostic)
```

System-user routes use the normal Runory session and Workspace membership.
External-user routes use the customer-access session and grant scope. There is
no public endpoint that accepts a `userId`, `contactId`, `grantId`, endpoint,
or arbitrary recipient selector and sends a push.

VAPID private material remains server-only. The public key may be returned by a
configuration endpoint or public environment value.

## 10. Delivery, retry, and diagnostics

- use the existing Outbox claim, retry, dead-letter, and operator diagnostics;
- retry transient provider/network failures with the existing bounded policy;
- do not retry permanent 400/401/403 failures until configuration is repaired;
- expire subscriptions on provider 404/410;
- record provider acceptance separately from display/read semantics;
- expose counts by active/expired subscription, notification category,
  accepted/failed delivery, and principal class without exposing endpoint data;
- provide a remote test result that distinguishes unsupported browser,
  permission denied, no subscription, server misconfiguration, provider
  rejection, and provider acceptance.

## 11. Delivery slices

### Slice A — Subscription foundation

- product-level manifest, `/app` principal-aware launch resolver, and root-scope
  registration with network-only safety tests;
- schema and sensitive subscription repository with endpoint hashing and
  diagnostic redaction;
- VAPID configuration and Web Push provider adapter;
- system-user subscribe/unsubscribe/status APIs;
- permission UI under mobile account/settings;
- Service Worker push/click handling;
- local and remote test actions.

### Slice B — Governed delivery

- `web` Message Delivery and `message_delivery.web_push` Outbox processing;
- preferences, retry, expiry cleanup, audit, and diagnostics;
- P0 system-user events and safe deep links;
- multi-device and re-subscription handling.

### Slice C — External customer reach

- customer-access subscription tied to an active grant;
- external-user preferences and P0 document/payment/service events;
- logout, revoke, expiry, and shared-device privacy handling;
- cross-tenant and cross-grant security tests.

### Slice D — Device acceptance and pilot

- installed-PWA checks on representative iOS and Android devices;
- foreground, background, closed-app, denied, disabled, expired, and offline
  scenarios;
- pilot measurement with at least one system user and one external user;
- support runbook and delivery diagnostics evidence.

## 12. Acceptance gates

v0.9.2 is not complete until:

1. a system user explicitly enables push and receives a server-originated P0
   notification on representative installed iOS and Android PWAs;
2. an authenticated external customer-access user can independently opt in and
   receive only events within their active grant scope;
3. an installed Runory PWA launches through `/app` into the correct authorized
   system-user, external-user, ambiguous-principal, or signed-out state;
4. notification click focuses or opens Runory and re-runs normal authorization;
5. denied permission, unsupported capability, missing VAPID configuration, and
   absent subscription have distinct recoverable states;
6. two devices for one principal work independently and one-device disable does
   not revoke the other;
7. revoked membership/customer access cannot receive subsequent pushes;
8. 404/410 endpoints are expired automatically and are not retried forever;
9. transient failures use Outbox retry and appear in existing diagnostics;
10. notification payloads and logs contain no sensitive business content or raw
   endpoint/key material;
11. cross-Workspace, cross-customer, arbitrary-recipient, and unsafe-deep-link
    attacks fail;
12. root-scope Service Worker tests prove that desktop, external-access,
    authenticated HTML, API, RSC, documents, and business data remain
    network-only;
13. Service Worker cache-policy and mobile performance gates do not regress;
14. delivery history distinguishes provider acceptance from user delivery/read;
15. local and remote test paths make the complete chain diagnosable;
16. at least one real v0.9 customer validates that the selected events improve
    operational response without unacceptable notification noise.

## 13. Explicit non-goals

- native iOS/Android binaries or platform-specific push SDKs;
- silent background data synchronization or offline command execution;
- SMS/email replacement or two-way messaging;
- marketing campaigns, broadcast audiences, segmentation, or growth messaging;
- arbitrary user-authored notification payloads;
- generic Workflow Builder notification nodes;
- guaranteed delivery/read receipts that Web Push cannot prove;
- rich confidential lock-screen content;
- location tracking, geofencing, live activity, or critical-alert entitlement;
- a second notification, retry, preference, or audit subsystem.
