## 1. Release decision

v0.9 is a verification and convergence version. The primary question is:

> Can the same product be delivered repeatedly to different customers without
> customer-specific Core forks?

v0.9 does not add new commercial shapes. It proves that the existing Reactive
Repair / Callout product can be provisioned, configured, extended, upgraded,
diagnosed, and supported as a repeatable operation — not a bespoke engineering
project per customer.

```text
reference solution (reactive-service)
→ automated workspace provisioning
→ pack + extension configuration
→ customer-specific 10% through governed extensions
→ upgrade without data or behavior loss
→ health check, diagnostics, and support tooling
→ payment reconciliation hardening
→ product and contract freeze
```

Engineering outcome:

> Harden the existing provisioning, migration, compatibility, rollout, and
> diagnostics foundations into repeatable delivery infrastructure. Do not
> introduce a second delivery platform, a second configuration model, or a
> parallel extension runtime.

## 2. Current-reality audit

The repository already has substantial delivery infrastructure from v0.6–v0.8.
The gap is not "build from zero" — it is "close specific gaps and prove
repeatability through real customer evidence."

| Area | Existing evidence | v0.9 gap |
| --- | --- | --- |
| Catalog release channels | `internal → beta → stable` promotion, deprecation, withdrawal, immutable locks | Policy documentation for v0.9.3 |
| Compatibility reporting | 6-check report (core, dependency, permission, schema, extension, migration risk), persisted, Admin UI | Deep integration with rollout preflight gate |
| Extension isolation | `module_owned` vs `workspace_extension`, namespace isolation, extension point validation, zero Core fork enforcement | Vocabulary unification in v0.9.3 |
| Command contract repair | Single/all-workspace check, batch backfill with preflight | Extend to comprehensive health check |
| Workspace export/import | Configuration-level export/import with dry-run validation | Not a general business-data migration framework |
| Rollout engine | Allowlist/percentage/all-eligible targets, auto-pause, pause/resume/cancel | Upgrade executor and pack-level rollback |
| Pack install/uninstall | Dependency resolution, DDL migration, demo data, fire-and-forget + polling | End-to-end provisioning orchestration |
| Outbox diagnostics | Pending/failed messages, retry, dead-letter, operator reset | Aggregate into support diagnostics package |
| v0.4→v0.5 migration | Idempent inventory→migrate→enable→verify with conflict detection | One-time tool, not a reusable framework |

### 2.1 Critical gaps to close

1. **Workspace-to-workspace configuration Diff** — compare a reference workspace
   against a customer workspace to verify 90/10 coverage. No existing tool does
   this; the current Diff is catalog version-to-version or extension plan-to-current.

2. **Rollout upgrade executor** — `updateRolloutTargetStatus` is a passive
   callback hook, but the active orchestrator that drives DDL migration + data
   migration + command contract re-sync per rollout target is not implemented.

3. **Automated end-to-end provisioning** — no CLI or API orchestrator that
   combines workspace creation + pack installation + extension configuration +
   seed data into a single repeatable operation.

4. **Support diagnostics package** — no single export that aggregates
   configuration + contract inventory + compatibility report + rollout status +
   outbox failures + migration state + installation errors.

5. **Comprehensive workspace health check** — current repair is limited to
   command contracts; no schema drift, stale views, or entitlement integrity
   checks.

6. **Payment reconciliation (V09-FIN-01)** — no `payment.reconcile` Command,
   discrepancy result type, or operator resolution flow.

## 3. Binding scope

### 3.1 v0.9.0 — Real FSM Customer Cohort

```text
3–5 real FSM businesses
canonical Reactive Repair / Callout shape
multiple compatible repair/service industries where practical
measure implementation time, support load, reliability, adoption, and business outcomes
```

Product track:

- onboard 3–5 real FSM businesses onto Runory Cloud;
- each customer uses the canonical Reactive Repair / Callout journey end-to-end;
- customer-specific configuration through Packs + Workspace Extensions only;
- zero Core forks per customer (binding red line);
- collect implementation time, support hours, system reliability, adoption
  rate, and business outcome metrics.

Engineering track:

- **automated workspace provisioning orchestration** — combine workspace
  creation + pack installation + extension configuration + seed data into a
  repeatable CLI/API operation;
- **support diagnostics package** — single export aggregating configuration,
  contract inventory, compatibility report, rollout status, outbox failures,
  migration state, and installation errors;
- **comprehensive workspace health check** — extend beyond command contracts to
  include schema drift, stale views, entitlement integrity, and extension
  consistency;
- **repeatability metrics collection** — instrument implementation time, manual
  interventions, support hours, and upgrade effort.

Exit: 3–5 real customers operate the canonical journey; each was provisioned
without Core forks; repeatability metrics are recorded; support diagnostics and
health check tooling are validated against real customer workspaces.

### 3.2 v0.9.1 — Reference Solutions and 90/10 Validation

```text
maintained reactive-service reference solution
customer variations assembled from Core + Modules/Packs + Workspace Extensions
no customer solution may fork Runory Core
measure standard product and governed extension coverage
```

Product track:

- maintain a standard `reactive-service` reference solution as a versioned,
  installable configuration (pack combination + extension template + seed data);
- assemble each v0.9.0 customer's variation from Core + Modules/Packs + Workspace
  Extensions;
- verify that no customer solution required a Core code change;
- measure the 90/10 ratio: percentage of requirements satisfied by standard
  product vs governed extension.

Engineering track:

- **workspace-to-workspace configuration Diff** — compare a reference workspace
  against a customer workspace, producing a structured Diff of objects, fields,
  views, navigation, extensions, permissions, and pack versions;
- **90/10 coverage report** — automated analysis of the configuration Diff,
  classifying each delta as "standard product", "governed extension", or
  "requires Core change" (which must be zero);
- **extension template library** — standard, versioned extension templates for
  common customer-specific needs (custom fields, views, navigation, workflows).

Exit: each v0.9.0 customer's workspace passes the 90/10 validation; the
reference solution is versioned and installable; zero Core forks are evidenced
through the configuration Diff.

### 3.3 v0.9.2 — Minimum Payment Reconciliation

```text
compare Runory Payment/Invoice settlement with one provider snapshot
show consistent, divergent, or unknown status to authorized operators
recover supported missed/reordered provider events through named Commands
preserve tenant, provider-account, currency, allocation, refund, and audit invariants
exclude bank/accounting/payout/fee/tax/dispute systems
```

This implements `V09-FIN-01` from the
[v0.6–v0.7 External Benchmark Retrospective](../releases/v0.6-v0.7-external-benchmark-retrospective-2026-07-27.md).

Required scope:

1. `payment.reconcile` Command — retrieve the current provider snapshot for one
   Workspace Payment and compare provider account, reference, currency, amount,
   payment status, and refunded amount with Runory authority;
2. `ReconciliationResult` — persist an auditable result of `consistent`,
   `divergent`, or `unknown`, with safe diagnostic details that never expose
   credentials or sensitive provider payloads;
3. operator visibility — expose reconciliation results to authorized operators
   through the existing diagnostics surface;
4. `payment.replay_event` Command — allow only named, idempotent reconciliation
   and replay actions that preserve legal transitions and existing Invoice
   allocation invariants;
5. test matrix — lost, duplicate, delayed, reordered, and refund events plus
   cross-tenant and wrong-provider-account rejection.

Explicit non-goals (binding):

- bank-statement or bookkeeping reconciliation;
- general ledger, journal entries, credit notes, or accounting export;
- payout, balance, settlement, fee, tax, or dispute management;
- bulk repair through direct database mutation;
- a provider-specific mutation path outside Commands and audit.

Exit: a missed provider event becomes an operator-visible discrepancy; a
supported replay action converges Payment and Invoice state idempotently; an
unsupported mismatch remains visible and requires escalation; repeated
reconciliation does not duplicate Payment, allocation, refund, domain event, or
audit outcome.

### 3.4 v0.9.3 — Product and Contract Freeze

```text
remove duplicate capabilities and inconsistent object models
unify lifecycle, error, permission, UI, and Agent-tool conventions
freeze supported APIs, MCP contracts, Pack manifests, and extension contracts
publish compatibility, upgrade, deprecation, and known-boundary policies
upgrade earlier customer solutions without data or behavior loss
```

Product track:

- **duplicate capability removal** — identify and remove any parallel models,
  inconsistent object shapes, or redundant infrastructure admitted during
  v0.5–v0.8 iteration;
- **vocabulary unification** — unify lifecycle, error, permission, UI, and
  Agent-tool vocabulary across all surfaces;
- **policy publication** — publish compatibility, upgrade, deprecation,
  known-boundary, and end-of-life policies;
- **early customer upgrade** — upgrade all v0.9.0 customers to the frozen
  product without data or behavior loss.

Engineering track:

- **rollout upgrade executor** — active orchestrator that drives DDL migration +
  data migration + command contract re-sync per rollout target, calling
  `updateRolloutTargetStatus` on success or failure;
- **pack-level rollback** — coordinated rollback of a pack version upgrade,
  reversing DDL migrations and restoring prior configuration;
- **contract freeze enforcement** — machine-auditable tests that prevent
  breaking changes to frozen APIs, MCP contracts, pack manifests, and extension
  contracts;
- **upgrade verification** — automated verification that a customer workspace
  retains data integrity and behavioral equivalence after upgrade.

Exit: all v0.9.0 customers are upgraded to the frozen product without data or
behavior loss; compatibility, upgrade, deprecation, and known-boundary policies
are published; contract freeze tests prevent regressions; the product is ready
for v1.0 GA preparation.

## 4. Explicit non-goals

- new commercial shapes (Recurring Service, Project/Installation);
- a second delivery platform or parallel configuration model;
- a general business-data migration framework (workspace configuration
  export/import remains the scope);
- a full customer portal beyond v0.8 customer access;
- application fees, Destination Charges, or payment marketplace expansion;
- Agent-generated official Module/Pack/Template productization;
- public marketplace or general plugin ecosystem;
- rebuilding existing foundations under new names;
- broad Cloud-to-Local deployment automation;
- full Workflow Builder or a second Workflow Runtime.

## 5. Execution sequence

```text
v0.9.0  Provisioning + health check + diagnostics + real customer cohort
v0.9.1  Configuration Diff + 90/10 validation + reference solution
v0.9.2  Payment reconciliation (V09-FIN-01)
v0.9.3  Upgrade executor + rollback + contract freeze + policy publication
```

v0.9.0 and v0.9.1 may overlap: customer onboarding (v0.9.0) informs the
reference solution (v0.9.1), and the configuration Diff (v0.9.1) is validated
against real customer workspaces (v0.9.0).

v0.9.2 is independent and may be developed in parallel with v0.9.0/v0.9.1.

v0.9.3 depends on v0.9.0 customer evidence and v0.9.1 validation results.

## 6. Repeatability metrics

Track at minimum:

| Metric | Target | Source |
| --- | --- | --- |
| Elapsed time from new Workspace to accepted reference solution | < 4 hours | Provisioning orchestration logs |
| Requirements satisfied through configuration, Pack, and Extension | ≥ 90% | 90/10 coverage report |
| Core changes required per customer | 0 | Configuration Diff + Git audit |
| Manual migration and upgrade interventions | ≤ 2 per customer | Upgrade executor logs |
| Failed or rolled-back installations/upgrades | 0 after v0.9.3 | Rollout engine state |
| Support hours during onboarding and first 30 days | < 20 hours per customer | Support diagnostics package |
| Shared Product Surface and workflow components reused | ≥ 80% | Configuration Diff |
| Payment reconciliation false-positive rate | < 5% | Reconciliation audit logs |

## 7. Stop rules

Remove an item from v0.9 when:

- it does not prove repeatability or convergence;
- it duplicates an existing delivery capability;
- it requires a generic platform before three customers need it;
- it primarily serves hypothetical future customers rather than the v0.9.0 cohort;
- it introduces a second model for something the existing foundation already does;
- it cannot be validated against at least one real customer workspace.

The default for attractive infrastructure capabilities is Defer to v1.0 or
post-1.0 unless a v0.9.0 customer immediately needs them.

## 8. Definition of done

v0.9 is complete when:

- 3–5 real FSM businesses operate the canonical Reactive Repair / Callout
  journey on Runory Cloud without Core forks;
- each customer's workspace passes the 90/10 validation (≥90% standard product,
  ≤10% governed extension, 0 Core changes);
- a `reactive-service` reference solution is versioned and installable;
- payment reconciliation (`V09-FIN-01`) is implemented and tested;
- automated workspace provisioning, health check, and support diagnostics
  tooling are validated against real customer workspaces;
- all v0.9.0 customers are upgraded to the frozen product without data or
  behavior loss;
- compatibility, upgrade, deprecation, and known-boundary policies are published;
- APIs, MCP contracts, Pack manifests, and extension contracts are frozen with
  machine-auditable enforcement;
- repeatability metrics meet the documented targets;
- the product is ready for v1.0 GA preparation.
